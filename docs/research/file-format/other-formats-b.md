## 1. LSM and embedded databases

### 1.1 RocksDB / LevelDB SST (BlockBasedTable) *(recalled; rocksdb wiki "Rocksdb BlockBasedTable Format")*

**Layout.** `[data block]* [meta blocks: filter, properties, ...] [metaindex block] [index block] [footer]`. The footer is fixed size (48 B for v0, 53 B for newer versions): a checksum type, two `BlockHandle`s (offset varint + size varint) for the metaindex and the index, a format version and a magic number. Every block is followed by a 5-byte trailer (1 byte compression type + 4-byte CRC32c). The reader opens a file with one fixed-size tail read.

**Data block.** Default 4 KiB (uncompressed target). Entries are `shared_len varint | unshared_len varint | value_len varint | key_delta | value`. Every 16th key (`block_restart_interval`) is a **restart point** stored in full, with `shared_len = 0`. A trailer holds `u32 restart_offsets[]` and `num_restarts`. Lookup binary-searches the restart array (whole keys), then scans at most 16 entries linearly. RocksDB can also add a hash index (`kDataBlockBinaryAndHash`) inside the block, about 4.6% space for 75% utilisation and one probe per point read.

**Index block.** One entry per data block: a *shortened separator key* (>= last key of the block, < first key of the next) plus a BlockHandle. The separator is the shortest string that sorts between the two, so the index is much smaller than full keys. It is itself a restart-point block.

**Partitioned index and filters** (`kTwoLevelIndexSearch`, `partition_filters`). With large files (hundreds of MB) the single index block gets too big for the cache, since every lookup would have to load it all. The top-level index (small, pinned in memory) points to index partitions of about 4–16 KiB, and filters partition the same way, one filter partition per index partition. A lookup costs top-level (cached), one index partition, one filter partition, one data block. This is a 4-level, 3-dependent-read path in the worst case.

**Filters.** Bloom (legacy full filter: ~10 bits/key gives ~1% FPR; "fast local bloom": cache-line-local, all probes in one 64 B line) and **Ribbon** (`ribbon_filter` since 6.15, about 30% less space than bloom for the same FPR, 3–4× more CPU to build, so it is recommended only for the cold levels). Filters are built over *key prefixes* when a `prefix_extractor` is set.

**Block cache.** An LRU/Clock cache, sharded, with a separate high-priority pool for index and filter blocks. Compressed-block secondary cache (v7).

**Steal.**
- **Separator keys in the sort-key index** (shortest-separator rather than the first key). For 16-byte random trace IDs a 4–6 byte prefix is enough, so the index is 3–4× smaller. README's "first key of every block" is fine for fixed 16 B keys (Elias–Fano on a prefix is better), but variable keys need this. [B, E]
- **Restart-point + hash-in-block** is not needed for fixed-width keys. Mostly avoid: our narrow blocks are columnar.
- **Partitioned index and filters** matter once a file is large (> ~1 GB). README's single "contiguous bloom section" is right for files of 100–500 MB. For bigger files add a two-level layout: the top level is `(first_key, offset)` per 4 KiB partition, and the filter is partitioned alongside it. Cost to add later: low, since it is just a section type. [B, E]
- **Ribbon filter instead of split-block bloom for the cold bloom section** (30% smaller, read-only after build). Worth it for ID bloom filters on immutable files. Cost: medium (Ribbon solver code, ~500 LOC). Gain: ~30% of a ~1.2 B/key filter. Small. [B, E]
- **Per-block checksum trailer with compression-type byte**: the README already has xxh3 per segment.

**Avoid.** Row-oriented blocks, plain entry-at-a-time lookup. Our data is columnar.

### 1.2 SQLite b-tree pages *(recalled; sqlite.org/fileformat2.html)*

Fixed page size (default 4096). A table b-tree is keyed by rowid, and interior pages hold `(child page, rowid)`. Leaf cells: `varint payload_len | varint rowid | payload | overflow page ptr`. A payload larger than `X = U − 35` (U = usable page size) spills the remainder into a **linked list of overflow pages**, so a large value is stored contiguously nowhere. The record header is a varint array of "serial types" (e.g. 0 = NULL, 1–6 = int of 1–8 B, 8/9 = constants 0/1, `N ≥ 12` even = BLOB `(N−12)/2`, odd = TEXT).

**Steal.** The **serial type per value that encodes constant/NULL/width in the type code**. This is the idea behind "constant" and "small int" block encodings and is already in the README (constant, sparse). Nothing structural else. **Avoid** overflow chains: a large value read costs N dependent reads, the worst thing for S3. The README's frame-list-in-row design (all frame offsets known after one read) is the right inverse.

### 1.3 DuckDB storage *(recalled; duckdb.org/docs/internals/storage)*

A single file with a header (two alternating 4 KiB "database headers" with a checksum, giving atomic root switching) and **fixed 256 KiB blocks** (`DEFAULT_BLOCK_ALLOC_SIZE`). **Row groups** of 122,880 rows (= 60 × 2048 vectors). Each column inside a row group is cut into **segments**, and each segment is chosen per column by trying candidate compressions (Constant, RLE, Dictionary, Dict-FSST, FSST, BitPacking, FOR, Chimp, Patas, ALP/ALP-RD, Roaring for validity). It analyses the data on the first pass and compresses on the second. Zone maps (min/max) are stored per segment as `BaseStatistics`. ART (adaptive radix tree) indexes are in-memory-first, serialized on checkpoint, used only for PRIMARY KEY/UNIQUE and point lookups, and they are bypassed by scans. Blocks are not self-describing: a separate metadata block pointer chain describes them.

**Steal.**
- **Two-pass (analyze then compress) per segment**: the README's "chosen by sampling" is the cheaper variant. DuckDB's full-analysis choice improves ratio 5–15% *(recalled)* at about 2× the encode CPU. Optional "tight" mode for compaction output, where CPU is cheaper than bytes. [D]
- **Fixed-size blocks = unit of I/O and of cache**: not for us (variable blocks win on S3).
- **ART**: not needed; a sorted file does not need a tree. **Avoid.**
- **Alternating double header for in-place commit**: irrelevant for immutable files.

## 2. Columnar engines

### 2.1 ClickHouse MergeTree (source cited)

**Parts.** A part is a directory, immutable once written. Two formats, chosen by size: **Compact** (all columns in one `data.bin` plus one `.mrk3`) below `min_bytes_for_wide_part` (default 10 MiB for non-debug builds: `src/Storages/MergeTree/MergeTreeSettings.cpp:37,78`; `min_rows_for_wide_part` default 0, `:85`) and **Wide** (a `.bin` + `.mrk2` per column) above it. Compact exists because many tiny parts × many columns × 2 files each is an inode and request disaster, which is exactly the S3 concern: **small files should be one object, big files can be many**.

**Granules and marks.** The sparse primary index has one entry per **granule** (default 8192 rows, `index_granularity`; and since "adaptive granularity" also capped at `index_granularity_bytes` = **10 MiB**, `MergeTreeSettings.cpp:1903`; a granule closes when either limit is hit; floor `min_index_granularity_bytes` = 1024 at `:1908`). `primary.idx` stores the *full sort-key columns of the first row of every granule*, kept entirely in memory (`MergeTreeDataPartWriterOnDisk.cpp:268` comment about the in-memory index living for the part's lifetime). A **mark** is `struct MarkInCompressedFile { size_t offset_in_compressed_file; size_t offset_in_decompressed_block; }` (`src/Formats/MarkInCompressedFile.h:17-20`), plus (adaptive format `.mrk2`/`.mrk3`) `rows_in_granule`. That is 16–24 B per granule per column. The addressing is two-level because ClickHouse compresses its **column stream in independent compressed blocks of ~64 KiB–1 MiB** (`min/max_compress_block_size`), and a granule begins at an arbitrary byte inside a decompressed block. So *granule size (row skipping) and compression block size (I/O) are decoupled*: any granule start is a `(block_offset, offset_inside_block)` pair. A lookup reads the one or two compressed blocks covering the granule.

**Skip indexes** (`GRANULARITY n` = one skip-index entry per n granules): `minmax`, `set(max_rows)`, `bloom_filter(fpr)`, `ngrambf_v1(n, size_bytes, hashes, seed)`, `tokenbf_v1(size, hashes, seed)` (`MergeTreeIndexBloomFilterText.cpp:1052,1063` validate the 4 and 3 arguments), and the newer **text index** (`MergeTreeIndexText.h:30-75`): an inverted index with *infinite granularity*, a sparse index of the first token of each dictionary block → block offset, **front-coded** dictionary blocks, posting lists as **Roaring bitmaps** or delta + bit-packed blocks (`MergeTreeIndexTextPostingListCodec.h:25-28`), a threshold below which short posting lists are **embedded in the dictionary block** (`:60-63`), and notably "unlike other skip indexes, the text index **can be merged instead of rebuilt** on a part merge" (`:36-38`). The older ngrambf/tokenbf are bloom filters sized by hand: one bloom per index-granule of n×8192 rows; sizing it wrong produces filters that are all-ones (useless) or wastefully large. This is a documented operational failure mode.

**Merges.** Parts are merged by k-way merge on the sort key. There are two algorithms. **Horizontal** merges all columns at once. **Vertical** merges key columns first, recording the *row-source order* (one byte per row, which part it came from), and then merges each remaining column on its own by replaying that order, so memory is bounded by one column at a time. It is used when `vertical_merge_algorithm_min_rows_to_activate` (default 16 × 8192 = 131,072 rows, `MergeTreeSettings.cpp:1826`) and a column count threshold are exceeded. `max_merge_delayed_streams_for_parallel_write` (default 40, `:85-90`) bounds the in-flight column streams.

**Steal.**
1. **Row-source map for vertical merge** (merge on key columns only, then replay a 1-byte-per-row permutation per column). This gives column-at-a-time memory and works with the README's frame-copy compaction: keys decide the order, payload columns are rewritten by reference only. [D] **Not in README** (the README says "copy frames" but not how the merge order is applied to many wide columns).
2. **Two-level addressing `(compressed block offset, offset in decompressed block)`**: decouples the skip granule (e.g. 8k rows) from the compression block (e.g. 64–256 KiB). Strata ties zone map = block. With a 16 B ID column that is 128 KiB per 8192 rows, but a status enum is 8 KiB, so a block of 64 KiB holds 64k rows and a zone map over 64k rows is too coarse for an enum filtered with a time range. Option: **sub-block zone maps** (one min/max per 4–8k rows inside a block, stored in the block header). Cost: low. [A] **Not in README.**
3. **Compact vs wide parts** (small file = single stream of all columns). For D: freshly flushed files (1–10 MB) should put everything in one contiguous region per row range so a lookup is 1–2 requests; compaction output switches to per-column layout. Strata's block order "(row range, column)" already is this, so it is essentially in the README, but not named as a size-dependent choice. [D, E]
4. **Mergeable text index** (the new ClickHouse one merges token dictionaries instead of re-tokenising). Our trigram frame filters (2 KiB per frame) are copy-merged with the frame, so we already have the same property for the payload layer. Confirms the design.
5. **Embed tiny posting lists in the dictionary** and **front-code the dictionary**. Relevant only if we add a token index (§ 3).
6. **Avoid**: hand-sized ngrambf. The README's per-frame filter sized from the unique-trigram count is better.

### 2.2 Lance v2 (primary: Lance paper arXiv 2504.15247; lance.org/format/file/encoding)

**Layout.** No row groups: "a file behaves as a single row group". Each column has one or more **disk pages** (default write: 1 Mi rows per file and an 8 MiB disk page), and a footer holds per-column metadata; there is a column-metadata offset table so only needed columns' metadata are read. Page-level encodings are cascaded.

**Structural encodings, chosen by value width** (this is the main idea):
- **Mini-block** (small values): values are split in chunks sized to **one or two disk sectors, 4–8 KiB compressed**; "at most 32 KiB and usually 4–8 KiB"; at most 4,096 values per chunk (power-of-two counts except the last; `LANCE_MINIBLOCK_MAX_VALUES` tunable up to 32,768). Chunk metadata is 2 bytes per chunk (12 bits = size in 8-byte words, 4 bits = log2 value count). A reader holds a **search cache of 24 B per chunk (41 B with a repetition index)**, so random access costs exactly **1 IOP** for a scalar, 2 for variable-width lists (rep-index then chunk). The paper's budget: search cache ≈ 0.1% of data size. Lance 2.2 raised the minimum chunk to 64 KB for some types.
- **Full-zip** (values ≥ 128 B in the paper, 256 B per the current docs): rep/def levels and value bytes are *zipped* into one row-major buffer with a 1–4 byte control word per value, so no chunk decompress is needed and one value = one read (2 IOPs if variable width: rep-index then data, parallelisable). No search cache. Only "transparent" compression (per-value, e.g. LZ4/zstd at ≥ 32 KiB values, bit-packing) is allowed, since delta forbids random access.
- **Blob** layout for values ~≥ 1 MiB (images): data in a side file, one IO per value.

**Numbers.** Parquet default config random access = ~5,500 rows/s on small scalars, tuned (8 KiB pages, no dictionary) ≈ 350,000 rows/s, i.e. ~64× difference, and the disk peaks at ~850 K random 4 KiB reads/s. Parquet needs a 20 B/page search cache. Full scan: Lance 1.3–2× faster than Parquet on strings and prompts.

**Steal.**
- **Mini-block = I/O-sector-sized chunks with a tiny per-chunk descriptor, power-of-two row counts, and a flat array of `u16` size words.** The README's 64–256 KiB narrow blocks are right for scans but not for B lookups on S3. Our B workload is "5–200 contiguous rows", so a **two-tier block layout is attractive: the block is the scan unit (64–256 KiB), and inside it a chunk directory of 4–8 KiB mini-blocks (2 B each) lets a point lookup read only the chunk(s) holding the row range** via an S3 range GET. For a 16 B trace_id column with 8192-row zone: 128 KiB block → 16–32 mini-blocks → read 4–8 KiB instead of 128 KiB (~16–30× fewer bytes). Cost: medium; the chunks need independent decoding so FoR/delta bases restart per chunk (loses ~1–3% ratio). [B, E] **Not in README** (README says byte-sized blocks of 64–256 KiB and nothing finer).
- **Choose layout by width; the 128–256 B cutoff** is a data point for the README's 256 B payload threshold. Good agreement. The distinct idea is **full-zip for mid-size values (256 B to ~8 KiB)** — e.g. exception messages, tool names + args, user ids with long strings — values too big for block-FSST but too small for the payload layer's dedup machinery; they can sit row-major with a control word and a 1-IO lookup. [B, C] **Not in README** (it has only two layers).
- **A sorted file lets a lookup need only: key-index binary search → one (offset) per column** because the row range is contiguous. Lance does this with a repetition index (`u64` per chunk); Strata's block table gives the same. No change.
- **Avoid:** delta encoding in the mini-blocks that must be randomly read (use FoR bases per chunk); Lance's `1 Mi rows / 8 MiB page` default for write, which is what the README rightly rejects.

### 2.3 Meta Nimble *(recalled; github.com/facebookincubator/nimble)*

A file is a series of **stripes**, each stripe holds streams (each column is one or more streams: values, nulls, lengths). The footer is a flat list of stream offsets, and a **flatbuffer** footer avoids parsing cost (the same motive as README's zero-parse directory). Encodings are a *tree*: nullable → (indices, values), dictionary → (alphabet, indices), RLE → (run lengths, values), with selection by "trial encode on a sample, keep the best" (cascading, like BtrBlocks). Design goals stated by Meta: wide tables (thousands of columns; ML feature stores) and cheap metadata decode, plus an extensible encoding registry. It avoids the Parquet "per-page header" approach: a stream is a contiguous byte range per stripe per column with the chunk sizes in the stripe footer, so no page-header walk is necessary to find chunks.

**Steal.** Flat stream table in the stripe footer; nothing new vs README. **Avoid:** stripes as the unit for point lookup (same weakness as row groups).

### 2.4 ORC *(recalled; orc.apache.org/specification/ORCv1)*

File = stripes (default 64 MiB), each with **index data (row index every 10,000 rows)**, data streams, stripe footer. The **row index** has, per column per 10k-row group, min/max/sum/null-flag stats **and the stream positions needed to seek into the (compressed) stream**: for a compressed stream the position is `(compressed chunk offset, offset inside decompressed chunk)`, plus RLE-run position. That is ClickHouse's mark in a different outfit. Bloom filters (`BLOOM_FILTER_UTF8`) are stored per 10k-row group per column in the index area, so a bloom check needs the stripe's *index streams* (one range per column per stripe; for S3 this is 1 read per stripe). The file footer has per-stripe offsets and column statistics; `PostScript` is the tail (≤ 256 B) read first. ORC compresses in **chunks of 256 KiB** (`compress.size`), each with a 3-byte header giving length and an "original (not compressed)" bit.

**Steal.**
- **Stored "original" bit** in the 3-byte chunk header (skip decompress when it does not shrink). The README has `encoding u16` per block, so just include `raw` as an encoding. Trivial.
- **Positions as (compressed offset, offset in decompressed)**: same as ClickHouse; see § 2.1 idea 2.
- **Bloom per 10k rows (group)**, not per stripe: finer than the README's "bloom section per column" (which implies one filter per block anyway).
- **Avoid:** 64 MiB stripes; index area *before* data in each stripe forces a dependent read to find what to read.

### 2.5 Arrow IPC / Feather v2 *(recalled; arrow.apache.org/docs/format/Columnar.html)*

A file is `ARROW1` magic, a stream of messages (flatbuffer metadata + 8 (now 64)-byte-aligned body buffers), a **footer** listing all record batch blocks `{offset i64, metaDataLength i32, bodyLength i64}` (24 B each), then footer length + magic. Body buffers may be individually compressed (LZ4 frame or zstd) with an 8-byte uncompressed-length prefix, and -1 prefix means stored raw. 64-byte alignment lets the file be mmapped and used zero-copy.

**Steal.** **Fixed-width 24-byte block table** (same as README). **Alignment of buffers to 64 B** so decoded blocks can be used in place on local disk (mmap) with no copy: relevant for A on local disk where the README plans zero-copy `Utf8View`. Cost: a few % of padding, low. [A, E] Also **the "-1 length means uncompressed" convention.** **Avoid:** whole-batch granularity and no per-column-chunk statistics.

### 2.6 BtrBlocks (Kuschewski et al., SIGMOD 2023) *(recalled)*

- Blocks of **64,000 values** per column.
- Schemes: One Value, RLE, Dictionary, Frequency (a top-value + exceptions), FOR + bit-packing, **Pseudodecimal** (doubles as `digits × 10^-e` with exceptions, the ancestor of ALP), FSST for strings. **Cascades up to depth 3**: e.g. Dictionary codes → RLE → bit-packing.
- **Scheme choice by sampling**: 10 runs of 64 consecutive values from random places (640 values, 1%); pick the scheme with the best ratio on the sample. This beats a random sample because it preserves runs.
- Result: roughly the ratio of Parquet + zstd with ~2.2× faster decompression (≈ 7 GB/s) and, over S3, scan cost lower because decompression kept up with the 100 Gbit/s network (the authors' argument for "lightweight only").

**Steal.** Run-preserving sampling (10 × 64 consecutive values), the **depth-3 cascade limit**, **Frequency** (very good for token counts / enum columns where 95% of values are one) and **Pseudodecimal/ALP for the cost field**. These are in the README (cascade by sampling, Vortex model), so mostly confirmation. The concrete addition is **the sample shape (10 runs × 64)** and a **cascade depth cap of 3** to bound decode cost. [A]

## 3. Search and log engines

### 3.1 Lucene / Tantivy segments *(recalled; tantivy source and Lucene codecs docs)*

A segment is a set of immutable files: **term dictionary** (an FST in Tantivy: `term → term_info` where term_info = `{doc_freq, postings_offset, positions_offset}`; plus a block-compressed term-info store with 256-term blocks, delta-bit-packed), **postings** in blocks of **128 doc ids** (delta + bit-packed via SIMD-BP128, final partial block VInt), each block with a **skip entry** `{last_doc_id, block_max_term_freq, offset}`, so intersections and `advance(doc)` skip 128 docs at once; **doc values/fast fields** (column store: bit-packed with linear-interpolated codec, or dictionary-ordinals for strings); **stored fields** (the row store): documents in **blocks of 16 KiB** compressed with LZ4 or zstd (Tantivy supports a shared dictionary for zstd, and Lucene 8+ uses 16 KiB (`BEST_SPEED`) or 60 KiB (`BEST_COMPRESSION`) chunks with an LZ4 preset dictionary of 8 KiB); and a **skip-index over the doc store** (`checkpoints`: `(doc_id range → byte offset)`, delta-coded), so fetching a doc is 1 index lookup plus one block decode. Tantivy's `Directory` abstraction lets all of this sit on S3 with a few ranged reads.

**Steal.**
- **Doc-store blocks of 16 KiB with a per-block checkpoint index**: the same shape as README's 64 KiB frames. A 16 KiB size gives lower point-read amplification but worse ratio: the README measured 64 KiB at 17.1 MiB and the real-data run has 1 MiB at 10.1 MiB, so 16 KiB would be ~25 MiB without dedup, again confirming why we want dedup, not small frames alone. **Training the zstd dictionary on the frame sample** (Tantivy/Lucene's preset dictionary) is in the README (optional per-column).
- **Skip-list entries with block-max score** (`block_max_term_freq`): in our setting it is the equivalent of **zone map + count per posting block**. Only needed if we add an inverted index.
- **Doc values for string columns as ordinals into a sorted dictionary**: ordinal order = lexical order, so range and prefix predicates on the dictionary map to a code range. **Sorted file-level dictionaries** (the README says "file-level dictionaries" but not that they are *sorted*). With sorted dictionaries a `status >= 'e'`, `model LIKE 'gpt-4%'` and `ORDER BY model` run on codes, and zone maps over codes are range-comparable. Cost: low (sort at flush). [A] **Not in README** (it only says dictionaries).
- **Avoid:** a full inverted index of the payload text. It costs 30–100% of the raw text size (Lucene) and Quickwit's own results are not better. The trigram filter plus dedup is the right size/benefit point.

### 3.2 Quickwit splits and hotcache (source cited)

A **split** is one object on S3: `[bundle of tantivy files][bundle metadata (JSON file→byte-range map)][metadata length u32][hotcache][hotcache length u32][optional trailer: footer start u64 | version u32 | 'QWFT']` (`quickwit/quickwit-directories/src/bundle_directory.rs:40-70`). A reader fetches the tail (the **split footer**, typically ~ 1 MB, with one request, a `footer_offsets` known from the metastore, so it is *zero* extra round trips: the offsets come from the metadata DB) and from then on never asks S3 for the term dictionary index, the doc store index, or the fast field headers.

**Hotcache** (`hot_directory.rs:472` `write_hotcache`): at split-creation time it *opens the index, runs a warm-up access, records every `(file, offset, len)` read through a `DebugProxyDirectory` (`:477-505`), and stores exactly those byte ranges in the footer*, excluding slices that are large, i.e. it keeps only a range if the file name ends with `store` or `term` or the file is `< 10 MB` (`:511-526`). Reading a split then needs 1 ranged GET for the footer, then data.

**Steal.**
- **Trace-driven footer content**: instead of hand-choosing what goes into the tail ("directory + schema + postscript"), *replay a representative query set on the freshly written file and embed the ranges touched* (zone-map headers, key-index top level, file-level dictionaries, chunk directory of the sort-key column). Practical effect: a cold B lookup is `tail GET (≈ 64–512 KiB, includes the key index and the block table for the sorted columns) → data GET wave`. 2 dependent requests instead of 3. Cost: medium, but the file-format part is trivial (a "hot region" in the postscript: `hot_offset`, `hot_len`). [B, E] **Not in README as a mechanism** (README: "one tail read normally opens a file"). Recommend an **explicit size-budgeted hot section**: ≤ 1 MiB, written last, so one speculative 1 MiB tail GET returns postscript + directory + key index top-level + dictionaries.
- **Metadata (file offsets) kept in the metadata DB / catalog**, so the reader knows `footer_start` without a first probe read: for us the SQLite/catalog row for a file can carry `(size, hot_offset)`. [E] Cost: low. Mentioned in README? Not explicitly. 
- **Avoid:** a JSON bundle metadata (`BundleFileRanges` is versioned JSON, per the doc comment): our directory is fixed-width binary.

### 3.3 VictoriaLogs storage (source cited)

Parts are directories with fixed file names (`lib/logstorage/filenames.go:4-16`): `metaindex.bin`, `index.bin` (block headers, 128 KiB uncompressed index blocks: `consts.go:21`), `columns_header_index.bin` + `columns_header.bin` (per-block per-column headers), `timestamps.bin`, `values.bin` + `bloom.bin` (sharded in **128 shards**: `consts.go:13`: columns are hash-assigned to a shard file, so a part has ≤ 128 value files whatever the number of fields), and special `message_values.bin`/`message_bloom.bin` for the `_msg` field. A block is at most **2 MiB uncompressed and 8 Mi rows** (`consts.go:26-29`, though the comment notes it can exceed by 2× on merge), ≤ 2000 columns (`:35`). **Constant columns** (same value in every row of the block, ≤ 256 B: `consts.go:44-46`) live in the columns header, not in a data stream. **Bloom per column per block**: tokens hashed with **6 hashes and 16 bits per token** (`bloomfilter.go:14-18`), i.e. a 0.04 B… *each token costs 2 bytes; false-positive rate ≈ 0.0005 (0.05%)* by the standard formula (1 − e^(−6/16))^6 ≈ 0.0004. A query for the word `foo` hashes it and rejects every block whose bloom for that column lacks it, without reading `values.bin`. Tokens are words (split on non-word characters), not trigrams; a substring query that is not a whole word falls back to scanning, which is what VictoriaLogs does for `*foo*`.

**Steal.**
- **Per-block bloom over *tokens* in addition to trigrams**: token filters cost 16 bits × distinct tokens; trigram filters cost far more per frame since distinct trigrams ≫ distinct words (each 64 KiB frame ≈ 2 KiB in README, 3%; a token bloom for the same 64 KiB of text with ≈ 2k distinct tokens is ≈ 4 KiB at 16 bits/token, comparable). The token filter has a lower FPR for whole-word terms such as an error code or a model name, and is also usable by an equality predicate on a long string. The trigram filter supports *any* substring ≥ 3 chars. Cost: low if both are available; choose per column. [C] Partly in README (trigram only).
- **Constant-in-block columns stored in the header** and **size cap (256 B) for them**: the README's `constant` encoding with the value inlined in the block-table row or zone map (`zone_min == zone_max` and `null_count = 0` ⇒ constant, no data read). For `service.name`, `model`, `deployment` in a time slice, whole blocks never touch data. Trivial; **make it explicit**: if `zone_min == zone_max ∧ null_count == 0` skip the block data entirely for that column (return the zone value). [A, B] Cost: trivial. **Not in README explicitly.**
- **Column-hash sharding into N files/regions** (128 here): irrelevant to a single-object file, but it bounds *the number of streams* for wide/dynamic schemas. Ours: shredded map keys ≥ 5% already bounded; leftover keys go to the key/value list. Same effect.
- **Avoid:** bloom *by value* only (no ordering info): equality only.

### 3.4 Loki chunks + TSDB index *(recalled; grafana.com/docs/loki/latest/operations/storage/tsdb)*

A chunk holds logs of **one stream** (a unique label set), compressed in **blocks of ~256 KiB uncompressed (`chunk_block_size`, default 256 KiB), target chunk size 1.5 MiB** (`chunk_target_size`) with snappy/gzip/lz4/zstd. Block headers carry `(mint, maxt, offset, len, checksum)`, so a time-bounded query decompresses only blocks within the range. The **TSDB index** (Prometheus-derived, § 4.3) maps label set → list of `(chunk id, min time, max time, KB, entries)`, no log content is indexed: "grep" is brute-force over the chunks of matching streams, parallelised across thousands of chunk reads. The Loki 3 **bloom gateway** adds blooms over *n-grams (n=4 with skip 1)* of structured metadata and line content, built *per block of series*, to skip chunks entirely.

**Steal.** The **inverse design confirms ours**: indexing nothing and brute-forcing text is cheap only when the per-chunk bytes are small; the n-gram bloom was bolted on later at the chunk level. A **trace_id-keyed chunk** (one trace's rows grouped) is what the sort key already gives us. Nothing new; note that Loki's n=4 gram blooms are known to bloat (they added a "bloom compactor"): so keep trigram filters per 64 KiB frame, which bounds the filter at 3%. **Avoid** n-gram bloom per series over days of text.

### 3.5 GreptimeDB (source cited)

Parquet SST files with **separate index files in the Puffin container** (`src/puffin/src`: `blob_metadata.rs`, `file_metadata.rs`; Puffin is Iceberg's blob-bundle footer format) holding inverted, bloom (`src/index/src/bloom_filter/creator.rs`: per-segment bloom plus a trailing metadata blob, size accounted at `:242,346`) and full-text indexes. The index is a **sidecar object, built async and attachable later**, with its own `bloom_filter_size + meta + 4` trailer.

**Steal.** The README already puts indexes in lazy, separate sections. The additional idea: make indexes a **sidecar object keyed by file id** (`file.idx`) so an index can be added or rebuilt *after the fact* (e.g. building a trigram index on a column nobody searched until now) without rewriting data, and cached on its own tier. Cost: low-medium; cheap since sections already have offsets. [C, E] Partly in README ("lazy, optional").

### 3.6 Zoekt / Google Code Search trigram index (Russ Cox 2012; github.com/google/zoekt/blob/main/doc/design.md) *(recalled)*

Index = for each trigram, a sorted posting list of document (and, in Zoekt, *position*) offsets; a query for `needle` intersects posting lists of its overlapping trigrams. Code Search stores 3 bytes/trigram → posting lists delta-varint coded. **Zoekt improvements:** postings contain *file offsets*, and two *specific* trigrams (the first and last of the pattern, at distance `len−3`) are intersected with the distance constraint, i.e. a **positional check using only 2 postings lists**; the rarest trigram is chosen using its list length; the files are mmapped. Index size is ≈ 3.5× corpus before compression for position-ful postings (Cox: about 20% of corpus for document-level).

**Steal.** (1) **Choose the two rarest trigrams of the needle (with their offsets within the needle) and check only those** — in README's per-frame filter this means *"all trigrams must hit the bloom"*; for needles of 20 chars that is 18 probes, 18 FPs multiply to tiny FPR, fine; no change. (2) **Position-aware filtering** for frame-level index: instead of a bloom per frame, an exact **trigram → frame-id posting list per file** (a Zoekt-style index over unique chunks). Size: the README says 2 KiB per 64 KiB frame (3%). A posting-list index over *unique* chunks with 16-bit frame ids and ~1.5 B/posting is ~10–25% of text, 3–8× larger, and answers a needle with posting-list intersection (no frame scan at all, zero decompression for absent needles; but the bloom already gives that). The README's design is the right trade; the posting-list variant pays off only for very large files (> 10 GB payload) where scanning 3% of filters is itself slow. **Flag as optional two-level**: a *file-level* bloom (all trigrams of the file, ~1 KiB per MiB... ) to skip the whole file during search over many files. [C, E] **Not in README**: README's filter is per frame, with no per-file/column rollup, so a search across 1000 files reads 1000 files' filter sections. A **rollup filter** (union of all frame trigram sets: one bloom per column per file, size ~ distinct trigrams × 10 bits) in the *hot tail* lets whole files be skipped with 0 extra requests. Cost: low.
(3) Common trigrams (like ` th`) hit nearly everything; Zoekt/Code Search handle it by using the *rarest* trigrams first; we should skip probing the top-K most frequent trigrams (store their ids) since they never discriminate.

### 3.7 Suffix arrays, FM-index *(recalled)*

A suffix array supports substring search in O(m log n) and costs 4–8 B per text byte; an FM-index (BWT + sampled SA + occ tables) answers `count` and `locate` in O(m) with size ≈ 0.5–1× the text (compressed), but construction is O(n) with 5–10× memory and typical build speed ~ 20–50 MB/s, and every query step is a dependent random access (m steps for a needle of m chars: m dependent S3 round trips unless the structure is local). **Avoid** as the primary mechanism: dependent reads kill E, the build is 10× slower than the 414–469 MB/s of the payload encoder (README), and compaction cannot just merge two indexes (rebuild needed). A **per-frame** suffix array is the only plausible fit, and it is dominated by "decompress a 64 KiB frame and `memchr`/SIMD-search it" (≈ 10 GB/s, so ~6 µs per frame): nothing to gain. Dedup also removes the need.

## 4. Time-series formats

### 4.1 Gorilla (Pelkonen et al., VLDB 2015) *(recalled)*

Timestamps: **delta-of-delta** with a variable-length prefix code: `0` → 1 bit (dod = 0); `10` + 7 bits for dod in [−63, 64]; `110` + 9 bits ([−255, 256]); `1110` + 12 bits; `1111` + 32 bits. 96% of timestamps compressed to one bit in their data. Values: **XOR with the previous value**: `0` if equal (51% of values); else `10` + meaningful bits reusing the previous leading/trailing zero window, else `11` + 5 bits leading zeros + 6 bits length + the bits. Average 1.37 B per (timestamp, value) vs 16 B raw: 12× (paper's headline). Chunks are 2 hours, with no random access inside a chunk (decode from the start).

**Steal.** Delta-of-delta suits `start_time` only when spans arrive at a regular cadence; for our data, `start_time` sorted by (trace, start_time) is monotone only within a trace, so **delta-of-delta on `(end_time − start_time)` (duration) and delta against the trace's first span** are the useful transforms: sorted order is by trace id, so timestamps are only *clustered* by time bucket (the file is a time slice). The effective approach is FoR against the block min, which the README already lists. The only novelty: use **delta-of-delta + bit-packed** (not Gorilla's bitstream) for `Sequence`-like columns (e.g. `span_index`), and avoid Gorilla's **bit-level serial decoding** (~ 1 GB/s scalar, no SIMD). **Avoid** XOR bit streams for hot paths.

### 4.2 Chimp, Elf, ALP *(recalled)*

- **Chimp** (VLDB 2022): XOR approach with a 3-flag scheme and a 2-bit leading-zero class (rounded leading-zero counts into 8 buckets, 3 bits), and a check of "trailing zeros > 6" to decide whether to store only the center bits: ~ 30% better ratio than Gorilla on average and ~ 2× faster decode. **Chimp128** compares against the best of the previous 128 values (by low 14 bits hash) to catch periodic series.
- **Elf** (VLDB 2023): *erases* the low mantissa bits of decimal values, which restores a decimal representation by rounding (`α` digits recorded) to make XOR trailing zeros long; +ratio over Chimp/Gorilla on decimal data; slower.
- **ALP** (Afroozeh, Kuffó, Boncz, SIGMOD 2024): for each vector of **1024 doubles**, search the best exponent/factor pair `(e, f)` on a sample so that `v × 10^e × 10^-f` rounds to an integer `d` with `d × 10^f × 10^-e == v` exactly; store `d` via **FoR + bit-packing (FastLanes)** and the failing values as exceptions (`position u16`, raw `f64`). If most values fail (high-precision data), **ALP_RD** splits the 64 bits to a *dictionary-coded left part* (≤ 8 distinct, 3 bits) and a plain right part. Decode is SIMD at several values per cycle and typically **~ 10–100× faster than Gorilla/Chimp** with a *better* ratio on decimal-looking data (cost values like `0.000345` and money fit well).

**Steal.** ALP is in the README (Vortex's version). The additional idea is **two-level sampling: the `(e, f)` combination is chosen once per row-group/block, and only 5 top combinations are tried per vector** (ALP's cheap first-level/second-level sampling). Implementation cost: low if the encoder is ours. Our costs (`f64` USD with 6 significant decimals) are the exact ALP target: expected 8–14 bits/value after FoR instead of 64 (≥ 4–6×). [A, D]

### 4.3 Prometheus TSDB *(recalled; prometheus.io / tsdb/docs/format)*

A **block** = 2 h of data: `chunks/` (segment files up to 512 MiB), `index`, `meta.json`, `tombstones`. **Chunk** = `len uvarint | encoding byte | data | crc32 (Castagnoli)`; XOR chunks hold up to 120 samples (≈ 1.3 B/sample); the chunk reference is a single `u64` = `(segment file number << 32) | offset`. **Index file**: `[symbol table][series][label index][postings][postings offset table][TOC]`. *Symbols* = all distinct label strings sorted, referenced everywhere by **index in the sorted table** (the dictionary idea at file scale). *Series entries* are 16-byte aligned (so their ref = `offset/16` fits in u32); each lists label-name/value symbol refs and its chunks as `(mint delta, maxt delta, chunk ref delta)`, delta-coded against the previous chunk (varint). *Postings* for `label=value` are sorted `u32` series refs (not compressed on disk, big-endian). The *postings offset table* is sorted by label name/value and is **sampled in memory every 32 entries**, then the reader binary-searches the sample and scans ≤ 32 entries on disk, i.e. a "sparse in-memory index over a sorted on-disk table", the same as LevelDB restart points. Intersection of postings lists for `a=1 AND b=2` = merge-join. Compaction merges blocks by merging symbol tables, series (sorted) and rewriting postings, and **chunks are copied unless overlapping** (vertical compaction) — cf. the frame-copy compaction in README.

**Steal.**
- **Series (trace) as an interned entity: a `(trace_id → row range)` table** in a file whose rows are sorted by `(trace_id, ts)`: this *is* the sort-key index. The Prometheus idea beyond that: **16-byte-aligned entries so a reference is `offset/16` in a u32** → 64 GiB addressability in 4 B. For our block-table, offsets in `u64` cost 8 B × blocks; with 4 KiB-aligned segments a `u32` suffices up to 16 TiB: halves the block-table. Cost: trivial; savings: small (4 B × (columns × blocks) ≈ tens of KB). [E] marginal.
- **Sampled in-memory index over a sorted on-disk table (every 32nd entry)** for the trace id index: a 1 M-trace file with 16 B keys = 16 MB table; sampling every 32 → 0.5 MB sample, one 512 B read inside the table. Equivalent to README's "first key of every block". The **two-level (sample + page)** form is the fix for a big file. [B]
- **Avoid** uncompressed `u32` postings for any inverted index (use Roaring / bit-packed deltas as ClickHouse does).

### 4.4 InfluxDB TSM *(recalled; docs.influxdata.com/influxdb/v1/concepts/storage_engine)*

A TSM file: `[header 5 B: magic 0x16D116D1 + version][blocks...][index][footer: 8 B offset of index]`. Each **block** holds one series-key + field's values for a time range: `crc32 | type byte | timestamps (compressed) | values (compressed)` — 1000 points per block. Encodings: timestamps use **simple8b RLE** (delta-of-delta scaled by the largest power of 10 common divisor then **Simple8b**, which packs as many integers as fit into a 64-bit word with a 4-bit selector, 240 ones, 120 twos, ... 1 sixty-bit), floats Gorilla XOR, ints zigzag + simple8b, strings Snappy, booleans bit-packed. The **index** is sorted by key, and per key a list of `(min time, max time, block offset, block size)` (28 B each); the file's index is kept in memory (compact with a **sparse offset table of u32 key offsets** for binary search by key).

**Steal.** **Simple8b** (and its SIMD cousin, Simple-16/BP128): an integer pack that adapts to *varying bit widths inside a block* without per-miniblock headers: good for token counts with a few outliers (the README has FoR/bit-pack with presumably *patching* via exceptions, which is better for rare outliers; Simple8b is better for broadly skewed small ints). Cost: low (~150 LOC). Gain: 5–15% on skewed counters vs FoR *(estimate)*. [A, D] The **time-range-per-block index** `(min, max)` is our zone map. Nothing new.

**Smaller items, all cheap.**
- Add `raw` (stored uncompressed) as a block encoding, the ORC chunk-header / Arrow `-1` convention.
- Align segment starts to 64 B so decoded blocks can be used in place via mmap on local disk (Arrow IPC).
- Offsets in 4 KiB units as `u32` (Prometheus `offset/16` trick) halve the block table.

**Explicitly not recommended.** Inverted indexes over payload text (Lucene: 30–100% of text size), FM-index or suffix arrays (dependent reads, 10× slower build, not mergeable), SQLite-style overflow chains, ART, n-gram bloom per series over days (Loki's bloom bloat), bit-level XOR streams (Gorilla/Chimp: no SIMD, serial decode), fixed 256 KiB or 64 MiB stripes as the I/O unit.

**What the survey confirms in the README design.** Compact-vs-wide size-based layout (ClickHouse), stored size-targeted blocks (Lance/BtrBlocks), a mergeable text filter (ClickHouse's text index merges instead of rebuilding, and our frame-copy does the same), constant and dictionary-first columns (VictoriaLogs, Lucene), copy-not-recompress compaction (Prometheus blocks, ClickHouse vertical merge), and a hot tail (Quickwit).
