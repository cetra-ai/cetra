# Auth security review, 2026-11-15 (track D, P26)

This is track D's P26 independent security review (`docs/plans/d-meta-auth/07-security-review.md`). It ran on `origin/main` at f60b816 and was done by models that did not implement track D.

**Scope.** The scope is wider than D's P1–P25. It covers:
- every `RouteDef` in `http::access::routes()`, including the `Key`, `Pat`, `ControlPlane` and `/api/internal/*` routes;
- the OTLP gRPC admission;
- the admin control socket (`admin_socket.rs`);
- the auth paths added after D: per-org OIDC and SSO enforcement (P M5), control-plane tokens and internal endpoints (P M2/M3), the password reset fix for DE-2 (#103) and PAT cache eviction.

**Method.** Five read-only reviewers (Sonnet) split the 30 checklist items:
- 1–9;
- 10–16 for the account, org and project routes;
- 11–15 for the project data routes and MCP;
- the internal routes, per-org SSO and the admin socket;
- 18–30.

The coordinating reviewer (Opus) then re-read the code behind every finding before recording it. It also re-ran P18's suite (item 17), wrote throw-away tests for the bugs below, and kept them as regression tests. Paths are relative to `crates/server/src/` unless they say otherwise.

## Checklist

**Authentication**

1. **OK.**
   - Credentials come only from `Authorization: Bearer` (`auth/principal.rs:174-193,375-392`) and the `cetra_session` cookie (`auth/session.rs:156-167`).
   - Nothing reads a `?token=`, `?api_key=`, `X-Api-Key` or form field. P18's `assert_query_credentials_are_ignored` (`http/access_suite.rs`) passes.
   - The org-token PUT carries its signed token in the body by design (D-P-11).
2. **OK.**
   - Any `Authorization` header resolves only the bearer and returns before the cookie is read; a bad header is 401 even with a valid cookie (`auth/principal.rs:183-193`).
   - CSRF fires only for a `Session` principal or under `/api/auth/` (`http/csrf.rs:20-41`).
   - A bearer request never refreshes the session. N1 is the one route that reads the cookie anyway.
3. **OK.**
   - Opaque tokens (session, reset, verify, invite, setup) are 32 bytes from the OS RNG (`auth/secret.rs:107-112`, `bootstrap.rs:134`).
   - Keys and PATs use unbiased base62: 32 characters (about 190 bits), and 24 for `pk` (about 143 bits).
   - Only SHA-256 hashes are stored and looked up. The setup token is compared with `constant_time_eq` (`routes/auth.rs:154`).
4. **OK** for disabled users. #12 covers the instance-wide SSO enforcement.
   - Sessions of disabled users are excluded (`meta/web_sessions.rs:120-122`) and deleted on disable (`routes/admin.rs:217`).
   - PATs are refused on each request because the user is reloaded (`auth/principal.rs:339-349`).
   - Login gives the uniform 401 (`routes/auth.rs:245,255`), and OAuth refuses them (`auth/oidc/flow.rs:499`, `ee/org_sso/login.rs:382,399`).
5. **OK.** See #25 and #26.
   - Expiry is rechecked on every cache hit (`auth/principal.rs:247` for keys, `:317` for PATs).
   - Revocation evicts the cache on these paths:
     - key revoke (`routes/api_keys.rs:151`), PAT revoke (`routes/tokens.rs:167`);
     - password change (`routes/me.rs:146`) and password reset (`routes/auth.rs:391`), which closes DE-2 (#103);
     - OIDC link (`auth/oidc/flow.rs:435`);
     - org SSO enforcement (`ee/org_sso/login.rs:289`, `settings.rs:391,573`);
     - control-plane user deletion (`routes/internal_users.rs:240`);
     - control-plane org creation, new with #4.
   - The project and org state is rechecked on every route (`http/access.rs:577-591`), so a cached key of a dropped project cannot be used.
6. **OK.** See #21.
   - argon2id with m=19456, t=2, p=1 (`auth/password.rs:21-23`); rehash on a weaker hash (`:230-259`).
   - NFC on hash, verify and policy (`:98,125,162`).
   - One verification per attempt in every branch (unknown, disabled, no password, locked, real) through the dummy hash (`routes/auth.rs:250-266`).
7. **OK.** See #22.
   - Login answers a bare 401 in every failure branch (`routes/auth.rs:274-281`).
   - Forgot and resend answer 204 in every branch (`:441-531`).
   - Mail is sent from a spawned task.
8. **OK.** See #19 and #20.

## Fixed findings

### #1 — Cross-project rule names through evaluator delete

**Before.** `delete_evaluator` ran `rules_of_evaluator(conn, id)`, which has no project filter, before the project-bound delete. A member of project B could send `DELETE /projects/B/evaluators/<A's evaluator id>`. If any rule in A used that evaluator, the answer was 409 with `rules.<id>: <rule name>: uses this evaluator` for each of A's rules, and it also confirmed the id exists. Evaluator ids are UUIDv7 (74 random bits), so the attacker needs a leaked id.

**Fix.** The rule list is filtered to the resolved project, so a foreign id falls through to the project-bound delete and answers 404.

**Test.** `routes::evaluators::tests::delete_from_another_project_names_none_of_its_rules`.

### #2 — Connection PATCH moves the stored key to a new host

**Before.** `update_llm_connection` merged `base_url` and `adapter` over the stored row and kept `secret_enc` and the sealed headers. An org admin, or a read-write PAT of one, could PATCH `base_url` to a host they control and call `POST …/{id}/test`. The stored provider key (often the owner's) was then sent to that host. Evaluator webhooks already refuse the same move (`CONFIG_NEEDS_SECRET`).

**Fix.** A PATCH that sends `base_url` or `adapter` must also send `api_key`, else it is a 400 on `api_key`. The UI places that error under the key field. Spec 09 and the CHANGELOG say so.

**Residual.** Stored `extra_headers` values still follow a host change. Requiring them too needs a UI change, and is part of D-P28.

**Test.** `routes::connections::tests::patch_of_the_host_needs_the_key_again`; two existing tests now send the key with `base_url`.

### #3 — Connection delete reveals another org's connection in use

**Fix.** The connection is checked against the resolved org before `connection_in_use`.

**Test.** `routes::evaluators::tests::connection_delete_from_another_org_is_404_while_used`.

### #4 — Control-plane org creation keeps an unverified account's credentials

**Before.** With `auth.signup = open` and `require_email_verification = false` (the default is `invite_only`), someone could register the victim's email first. When the control plane then created an org for that email (D-P-29 reuses an existing user), the squatter's password, sessions and PATs owned the org.

**Fix.** An unverified existing user gets D148's treatment before becoming the owner: sessions deleted, PATs revoked and evicted, password cleared, email marked verified. A verified user is reused unchanged, as D-P-29 says.

**Test.** `routes::internal_orgs::tests::an_unverified_owner_loses_the_password_and_sessions`.

### #5 — A disabled owner counted as the last owner

**Fix.** The new `count_active_owners` (`meta/members.rs`) counts only owners whose account is enabled. A role change or removal that leaves no active owner is refused inside the transaction, and it rolls back. A disabled owner can still be removed while an active one stays. `count_owners` keeps its meaning for the control plane's `sole_owner_of`, where a disabled user being deleted must still count.

**Test.** `routes::members::tests::a_disabled_owner_does_not_keep_the_org_owned`.

### #6 — IPv4-mapped trusted proxy

**Fix.** The peer and each `X-Forwarded-For` entry go through `IpAddr::to_canonical()`.

**Test.** `http::client_ip::tests::an_ipv4_mapped_peer_matches_an_ipv4_proxy`.

### #7 — TOML syntax errors printed the line

**Before.** A throw-away test showed this error text for `[auth.github]` followed by `client_secret = hunter2`:

```
TOML parse error at line 2, column 17 | 2 | client_secret = hunter2 | ^ invalid string
```

**Fix.** `map_figment` keeps only the first line (`TOML parse error at line N, column M`) of a path-less TOML parse error.

**Test.** `config::tests::toml_syntax_errors_omit_the_line`.

### #8 — Invitation to an org that is not active

**Fix.** `accept_invite` and the invited signup answer as for a missing invitation when the org is not `active`.

**Test.** `routes::invites::tests::an_inactive_org_takes_no_member`.

## Fixed in the follow-up (D-P-66 to D-P-72)

The remaining high and medium findings were fixed after the review, one commit each. Each entry gives the choice taken; where the review's proposal left a product decision open, the most conservative option was taken.

### #9 (high) — The inviter could pre-create the invitee's verified account

The reproduction: an org admin invites `victim@corp.com`, signs up with the invitation token and their own password (the account is verified and works under `invite_only` with no SMTP), and keeps the password when the victim later links Google or GitHub.

**Fix (the user chose option b).** `users.email_verified_via` records `mail_token`, `idp`, `invite`, `control_plane` or `operator`. Linking an identity (instance providers and org SSO) clears the password, and revokes sessions and tokens, unless the email is proven by `mail_token`, `idp` or `control_plane`.
