# 04: user-triggered outbound calls answer 503 `restore_mode`

Read [00-design.md](00-design.md) first, especially § Restore mode (D-N-26).

**Goal:** in restore mode, every handler whose job is an outbound call answers `503` with the new problem code `restore_mode` before doing anything. The user sees why. Phase 03's choke points would refuse the call anyway, but with a confusing error or a timeout.

**Edit only:**

## Changes

### `ProblemCode::RestoreMode`

- Add `RestoreMode` with the doc comment `/// The server runs in restore mode: outbound calls are off (D-N-26).`
- Its wire name follows the enum's serde rule, which gives `restore_mode`; its status is 503.
- Add it everywhere `ProblemCode` is listed: `status()`, `reason_phrase()` (`"Service Unavailable"`), any `ALL` array or OpenAPI enum, and the spec 09 list.

### `ApiError::RestoreMode`

Handlers return `ApiError`, which has no variant for an arbitrary `ProblemCode` and no `From<Problem>`. Add one, after `Unavailable`:

```rust
/// Restore mode: this outbound call is off (D-N-26).
#[error("restore mode")]
RestoreMode {
    /// What is off, e.g. `"channel test"`. Static text.
    what: &'static str,
},
```

Its arm in `ApiError::problem()` is `Problem::new(ProblemCode::RestoreMode, Some(format!("{what} is off: this server runs in restore mode")))`. Add an arm to every other exhaustive `match` on `ApiError` (`grep -rn "ApiError::Unavailable" crates/server/src` shows where variants are matched).
- Run `just openapi` if the enum is in the OpenAPI document.

### `http/restore.rs`

```rust
//! Restore mode's answer for user-triggered outbound calls (N M3, D-N-26).

use crate::http::AppState;
use crate::http::error::ApiError;

/// `Err(ApiError::RestoreMode)` (503 `restore_mode`) when the server runs in restore mode.
pub(crate) fn refuse_outbound(state: &AppState, what: &'static str) -> Result<(), ApiError> {
    if state.config.restore_mode {
        return Err(ApiError::RestoreMode { what });
    }
    Ok(())
}
```

Adjust the `use` paths to where `AppState` and `ApiError` live. If a handler returns a different error type that wraps `ApiError`, use its existing `From<ApiError>` (`?` converts). `what` is a fixed string from the table below, never input.

### The handlers

Call `refuse_outbound(&state, "<what>")?` as the **first** statement of each handler. It goes after the extractors and before any database read, so a refused call does no work. If a handler has an access check that must run first, so that an unauthorised caller still gets 401/403, put the call right after that check. Say in the report which order you chose.

**Before writing**, check each handler:

- If `put_org_sso_provider` does **not** fetch the discovery document, remove its row and say so in the report.
- If a handler not in the table calls `egress().post`, `EvalRunner::run`, `Mailer::send_now`, an identity provider's `discover`/`exchange`, or the org-SSO `TxtResolver`, add it with a fitting `what` and report it.

Find them with:

```bash
grep -rn -E "egress\(\)\.post|eval_runner\.run|\.run\(RunInput|send_now|discover_async|exchange|txt_lookup|TxtResolver" crates/server/src --include=*.rs | grep -v -E "/tests?\.rs|mod tests"
```

Background paths (alert deliveries, the dispatcher) are covered by phase 03.

`/api/auth/sso/discover` only reads `meta.db`: it is not refused. The browser redirects to `/api/auth/sso/authorize` next, and that is refused.

**Not refused:**
- Invites, sign-up and password reset still answer as today, because their email is sent in the background and phase 03's `Transport::Off` logs and drops it.
- An HTML redirect flow (`authorize`, `callback`) gets the JSON problem. That is acceptable for a drill, and the UI already shows no provider buttons in restore mode.

## Tests

One test per row, each in the module that already tests that handler. Name them `<handler>_is_refused_in_restore_mode`.
- Build the app with `TestApp::with_config(|c| c.restore_mode = true)`, seed what the route needs (`app.seed()`, a channel, a connection, …) the way the existing tests of that handler do, and call the route as an authorised user.
- Assert:
  - `status == 503`;
  - `problem().code == ProblemCode::RestoreMode`;
  - the detail is `"<what> is off: this server runs in restore mode"`;
  - nothing happened: no delivery or job row, no email in `app.sent()`. For the channel and connection tests, point them at a local `TcpListener` and assert that it accepted nothing within 200 ms.

Also `refuse_outbound_passes_without_restore_mode`: a unit test in `restore.rs` that the function is `Ok` when the flag is off.
