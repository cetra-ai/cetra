# S · Cloud auth

Track S builds the three llmobs changes the cloud control plane (track Q, private repository `llmobs-control`) needs before its first paying customer (D180, D-P-43). Q's design lists them as requests R7, R13 and R16 (`llmobs-control/docs/00-design.md` § Requests to llm-observer):

| Request | What Q needs | Why | Q waits in |
|---|---|---|---|
| **R16** | The `client_secret` of one `[[auth.oidc]]` provider from the environment | Q keeps secrets in the cell's env file, not in `llmobs.toml` (D-Q-14) | nothing: Q writes `llmobs.toml` `0640 root:65532` until then |
| **R13** | With `auth.disable_password = true`, instance admins still log in with a password | cloud cells turn password login off (D-Q-19), but the operator's account is an instance admin, never linked to an OIDC identity (D148), and must reach the admin pages | Q2.27 |
| **R7** | With password login off and exactly one provider, the login page starts that provider at once (keeping `?redirect=`); the invite page does the same for a visitor without a session, with `redirect` back to the invite. Not when per-org SSO is in use (D-P-41) | on a cloud cell the only provider is the control plane (`oidc:cloud`); a page with one "Continue with …" button is a needless click, and an invitee without an account must come back to the invite after their first login | Q2.27 |

There is no design doc: the pieces exist (D's auth routes and config loader, L's auth pages, P's M5 email-first login and its `?password=1` break-glass path). The design fits in this README (§ Decisions). The plan has four sub-phases, **S1–S4**, one file each, one commit each, done in order by one agent working alone. Haiku implements, Sonnet reviews. Nothing in a phase file may need a guess: if the code differs from what a phase file quotes, stop and report instead of improvising.

## Decisions

The decisions are also recorded in `docs/mvp-decisions.md` § Track S.

| # | Topic | Decision |
|---|---|---|
| D-S-1 | Plan | **A README and four sub-phases, no design doc.** Server first (S1, S2), then the pages (S3, S4), so each web phase runs against a server that already behaves as the page expects. |
| D-S-2 | R16: the env form | **`LLMOBS_AUTH__OIDC__<NAME>__CLIENT_SECRET`, where `<NAME>` is the provider's `name` upper-cased with `-` written as `_`** (`cloud` → `LLMOBS_AUTH__OIDC__CLOUD__CLIENT_SECRET`, `my-idp` → `LLMOBS_AUTH__OIDC__MY_IDP__CLIENT_SECRET`). Names are `[a-z0-9-]`, so the mapping is one-to-one. The provider itself stays in `llmobs.toml`; `client_secret` there becomes optional, the variable wins over it (later sources win, spec 12), and a provider with neither is refused at load as today (`client secret is required`). Every other `LLMOBS_AUTH__OIDC__*` variable, and one naming no provider of the file, is a load error naming the variable (never its value), as an unknown `LLMOBS_` variable already is: until now they were silently ignored, so a typo left the TOML secret in force without a word. **No `client_secret_file`:** every other secret of llmobs is read from the environment (`LLMOBS_ENCRYPTION_KEY`, `LLMOBS_SMTP_URL`, `LLMOBS_LICENSE_KEY`, GitHub's and Google's split form), and Q keeps secrets in an env file (D-Q-14), so a file form would be a second mechanism for one key. |
| D-S-3 | R13: what instance admins keep | **Under `auth.disable_password = true`, an instance admin keeps password login, password change (`POST /api/v1/me/password`) and password reset through a link (`POST /api/auth/password/reset` with a token from `llmobs admin reset-password` or the admin users page).** Everyone else is refused as today. Self-service "forgot password" (`POST /api/auth/password/forgot`), password signup, invite signup and setup stay refused for everyone: an operator who forgot their password uses the CLI, as without SMTP. The login check runs **after the password verifies** and after the org SSO check (the order of D-P-58): an unknown email, a wrong password, a disabled account, an account without a password and a locked email all answer the same 401 as when password login is on (D145), and only a correct password of a non-admin answers `403 forbidden`. That 403 tells the caller the password is right; it is a deliberate exception to D145, the same as D-P-58's `sso_required`, and needs the password to begin with. So login under `disable_password` now hashes, rate-limits and counts lockout like any password login: it costs one Argon2 verification per request, as on any instance with password login on (the login limiter is per client IP and email, D143). The reset check runs after the token resolves to its user (`400` for a bad token, `403` for a non-admin, whose token stays unused). |
| D-S-4 | R13: what the config says | **`GET /api/auth/config`'s `password_enabled` stays one instance-wide flag: `false` under `disable_password`, for everyone.** The instance admins' way in is the existing break-glass URL **`/login?password=1`** (D-P-58, D-P-60), which now shows the password form also when `password_enabled` is false. The login page links to it ("Instance admin? Sign in with a password") whenever password login is off and the page does not start a provider at once. |
| D-S-5 | R7: when the login page starts the provider | **When `password_enabled` is false, `sso_discovery` is false and exactly one instance provider is listed** (GitHub, Google and every `[[auth.oidc]]` count; org providers never appear in `providers`), the login page leaves at once for `/api/auth/authorize/<id>` with the page's `?redirect=`. Not when the URL has `?password=1` (the admins' form), `?error=` (a failed provider login must show its message, or the page would loop through the provider) or `?signed_out=1` (D-S-6). `sso_discovery` true means an org provider routes some domain (P's M5, D-P-60): the email-first page stays. On a cloud cell org SSO is never granted (D-P-41), so `sso_discovery` is false there. The page leaves with `location.replace`, so Back from the provider returns to the page before `/login` instead of re-entering the redirect. While it leaves, it shows "Redirecting to <provider>…" and the provider's button in case the navigation is blocked. |
| D-S-6 | R7: signing out | **Sign-out lands on `/login` with the `signed_out` flag (`?signed_out=true`), which never starts a provider at once**: the provider usually still has its own session, so starting it would sign the user straight back in. The page shows "You're signed out." above the provider button. The router writes boolean search flags as `?signed_out=true` and `?password=true`; the parser accepts `1` and `true` alike, so `/login?password=1` typed by hand works. The same holds on the invite page after its "Sign out" button. Logging out of the provider itself (RP-initiated logout) is out of scope. |
| D-S-7 | R7: the invite page | **For a visitor without a session, under the D-S-5 condition, the invite page leaves at once for `/api/auth/authorize/<id>?redirect=/invite/<token>`**, both when the invited email has an account and when it does not, except when sign-up is `disabled` and the email has no account (the page keeps its "Sign-up is disabled" message: the provider would answer `signup_closed`). Under `invite_only`, a provider login of an email with a pending invitation creates the account (spec 08 § OAuth / OIDC; `has_pending_invite` in `crates/server/src/auth/oidc/flow.rs`), so the visitor comes back signed in and **clicks "Join <org>"**: accepting stays an explicit action, as for every other invitee. A failed provider login goes to `/login?error=<code>`, which does not start a provider again (D-S-5). After "Sign out" on the invite page (signed in as another account), the page shows the provider button instead of starting it (D-S-6). Known limitation: under `invite_only`, a provider login whose verified email is not the invited one ends at `/login?error=signup_closed`, and the invite link must be opened again. |
| D-S-8 | Scope | **Only the login and invite pages start a provider at once.** `/signup` and `/setup` keep their buttons (signup under `disable_password` has nothing but the providers; setup needs its token). S adds no config key and no API field. |

### Interaction with per-org SSO (P's M5)

- D-P-41: per-org SSO serves self-hosted instances; on a cloud cell the control plane is the only provider and `sso_discovery` is false, so R7 applies there. On a self-hosted instance with an enabled org provider and a verified domain, `sso_discovery` is true and the login page keeps P's email-first step (D-S-5).
- D-P-55: instance admins are never linked to an org's identity, as D148 for the instance providers. That is why R13 exists: an admin has no other way in than the password.
- D-P-58: under an org's enforcement, a non-admin's correct password answers `403 sso_required`. S2 keeps that check first and adds the `disable_password` refusal after it, so a user under both sees `sso_required` (the more useful answer). Instance admins are exempt from both. `/login?password=1` is the same break-glass URL for both.
- D-P-57 (Test sign-in of a disabled org provider) starts from the org's settings page with a session, never from the login page, so `sso_discovery` false with a disabled provider does not hide anything.

## What Q's Q2.27 can rely on

- `GET /api/auth/config` on a cell with `disable_password = true` reports `password_enabled: false` for everyone (D-S-4).
- The instance admin reaches the password form at `https://<cell>/login?password=1`, typed by hand (D-S-4). On a cloud cell `/login` leaves at once for `oidc:cloud`, so the page's "Instance admin? Sign in with a password" link shows only after a provider error or a sign-out: Q's runbook must give the URL, not point at the link.
- `POST /api/auth/login` of a customer without a password answers `401`; of a non-admin with a correct password `403 forbidden`; of the instance admin `200` (D-S-3).
- `POST /api/auth/signup` answers `403` under `disable_password`, as today.
- An invitee lands back on `/invite/<token>` signed in and clicks "Join <org>" (D-S-7): Q2.27's runbook text "land on the cell's invite, accepted" becomes "land on the cell's invite and click Join".
- `LLMOBS_AUTH__OIDC__CLOUD__CLIENT_SECRET` in the cell's env file replaces `client_secret` in `llmobs.toml` (D-S-2); a stray `LLMOBS_AUTH__OIDC__*` variable now stops the server at start.

## Not in S

- RP-initiated logout from the provider (D-S-6).
- A `client_secret_file` form (D-S-2), and env forms for the other `[[auth.oidc]]` keys.
- Starting the provider from `/signup` or `/setup` (D-S-8).
- Self-service password reset by email for instance admins under `disable_password` (D-S-3).
- A stronger login limiter. With password login live for admins, a caller varying the email can make the server run one Argon2 verification per request within the per-IP form limits, and can lock an admin's email for 15 minutes with 20 wrong passwords, as on any instance with password login on (D143); the admin recovers with `llmobs admin reset-password` or waits.
