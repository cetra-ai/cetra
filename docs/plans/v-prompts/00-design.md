# V · Prompt registry and playground — design

D191 moved the prompt registry and the playground into the MVP (it replaces D19 and amends D20). Track V builds both:

- a **prompt registry** per project: named prompts with numbered, immutable versions and mutable labels, stored in `meta.db`;
- **delivery** to applications: a REST fetch with an `sk` key, and `get_prompt()` in the Python and TypeScript SDKs with a cache, stale-while-revalidate and a fallback in code;
- **linking**: spans that used a prompt version carry it, traces can be filtered by it, and the UI shows cost, latency and scores per version;
- a **playground**: edit a prompt version, or open a recorded LLM span, run it against one to four models side by side through the org's LLM connections, stream the answers, trace each run into the project, and save the result as a new prompt version.

**Read first:** `AGENTS.md`; `docs/mvp-decisions.md` (D11, D18, D21, D22, D159–D163, D166, D172, D173, D178, D179, D185, D191, Track I, Track J, Track P, Track T, Track V); spec 01 (span and trace columns), 02 § Pipeline, 03 § 12 (format versions), 04 § Evaluation, 05 § Default exclusions, 06, 08 (roles, API keys), 09, 10, 11; `docs/plans/i-online-eval/00-design.md`; the competitor notes in [§ Competitors](#competitors).

This document holds the goals, the architecture, the decisions and the milestones. It has no implementation detail. Each milestone gets its own plan, written just before it starts, from the code that exists then. **Haiku implements the plans one phase at a time; Sonnet reviews them** (`~/.claude/CLAUDE.md`).

## Goals

1. A team keeps its prompts in cetra, not in code. It edits them in the UI or through the API, and every save is a new version that never changes.
2. An application fetches "the `production` version of `support-bot`" with one SDK call, keeps working when cetra is slow or down, and does not pay a network round trip on every call.
3. Moving a label (for example `production` from version 4 to version 5) deploys a prompt without a code release. Only project admins can move protected labels.
4. Every span that used a prompt version says so. Traces can be filtered by prompt version, and the prompt page compares versions on cost, latency, errors and scores.
5. The playground answers "what would this prompt (or this recorded call) do on another model, or with this edit?" in seconds, side by side, with cost and latency. A good result becomes a new version in one click.
6. Nothing in V weakens the existing guarantees: provider keys never reach the browser, every outbound call goes through the SSRF guard (D166), logs and errors never contain prompt text (`AGENTS.md` § Privacy), and the crate graph stays as enforced.

## Non-goals

These are out of track V. Each is a possible later track, and the design does not rule any of them out.

- **Logic in templates.** No loops, conditionals, filters or includes (D-V-3).
- **Prompt composition.** No references from one prompt to another, unlike Langfuse's `@@@langfusePrompt:…@@@`.
- **Folders.** No folder entities and no `/` in names (D-V-2).
- **Git sync and CLI commands** (`cetra prompts pull/push`), as in LangWatch.
- **Server-side label routing.** No A/B splits of a label between versions, and no gateway (D4).
- **Evaluators built from registry prompts.** The template syntax keeps this possible (D-V-3), but judges keep their own templates.
- **MCP tools for prompts.** See open question Q2.
- **Images, audio and files in the playground.** Only text and tool parts are sent (D-V-25).
- **Running tools in the playground.** The model's tool calls are shown, and the user can type tool results (D-V-25).
- **Saved playground sessions** shared between users. The draft stays in the browser, and the run history comes from the traces (D-V-28).
- **Running the playground over a dataset.** This is open question Q1, because it touches D18.
- **Prompt optimizers** (GEPA, MIPRO, DSPy).

## Architecture

### Parts and crates

The enforced crate graph (`AGENTS.md` § Layout) does not change. No crate gains a workspace dependency.

| Crate | What V adds |
|---|---|

The attribute names `cetra.prompt.name` and `cetra.prompt.version`. The reserved environment `cetra-playground` beside `cetra-eval`, behind one "is this environment reserved" test (D-V-22). `cetra-core` is a shared contract, so the coordinating session makes this change, or grants it in the milestone's brief. |
| `cetra-otel` | Normalization of the prompt attributes into the new columns: `cetra.prompt.*`, then Langfuse's `langfuse.observation.prompt.*` (D-V-16). A bump of the row `schema_version` (spec 01 § Normalization version). |

### Tables (`meta.db`, one migration)

Each milestone plan gives the exact SQL. Here are the shape and the contracts.

- **`prompts`**: `id` (UUIDv7), `project_id` (FK, cascade), `name` (unique per project, immutable), `type` (`text` or `chat`, immutable), `description`, `tags` (JSON array), `latest_version`, `created_by`, `created_at`, `updated_at`.
- **`prompt_versions`**: primary key `(prompt_id, version)`. Columns: `template` (a JSON string for text, a JSON array of messages for chat), `config` (a JSON object), `commit_message`, `created_by` (a user id, or `key:<key id>` when an API key wrote it, as `dataset_versions` does), `created_at`. Variables and placeholders are computed from the template when read. Rows are never updated. They are deleted only with their prompt.
- **`prompt_labels`**: primary key `(prompt_id, label)`. Columns: `version`, `updated_by`, `updated_at`. One label points to one version. A version can carry many labels.
- **`prompt_label_events`**: an append-only history of label moves. Columns: an integer `id` (its order is the history's order), `prompt_id`, `label`, `from_version`, `to_version` (null when the label was removed), `actor` (as `created_by`), and `at`. The prompt page shows it ("who promoted version 5 to production, and when").
- **`prompt_settings`**: one optional row per project holding `protected_labels`, a JSON array of label names. A project without a row protects `["production"]` (D-V-10).

### API (`/api/v1/projects/{project}/…`)

| Route | Who | What |
|---|---|---|
| `GET /prompts` | `View`, key `read` | List prompts with `q`, `tag`, `label`, and cursor paging: name, type, latest version, labels and their versions, tags, updated_at |
| `POST /prompts` | `ManagePrompts` | Create a prompt with its version 1: `{name, type, template, config?, labels?, commit_message?, description?, tags?}` |
| `GET /prompts/{name}` | `View`, key `read` | The prompt: type, description, tags, latest version, labels |
| `GET /prompts/{name}/resolve` | `View`, key `read` | **The fetch.** Resolves `?label=` (default `production`) or `?version=`. Both together is a 400. Answers the resolved version with a strong `ETag`, and `304` on `If-None-Match` (D-V-12) |
| `PATCH /prompts/{name}` | `ManagePrompts` | `description`, `tags` |
| `DELETE /prompts/{name}` | `ManagePrompts`; admin if any label on it is protected | Deletes the prompt, its versions, labels and history. Spans keep their name and version |
| `GET /prompts/{name}/versions` · `GET /prompts/{name}/versions/{n}` | `View`, key `read` | The version list (newest first, with labels) and one version |
| `POST /prompts/{name}/versions` | `ManagePrompts` (protected labels in `labels`: D-V-10) | A new version: `{template, config?, labels?, commit_message?}`. The type must match the prompt's |
| `PUT /prompts/{name}/labels/{label}` · `DELETE …` | `ManagePrompts`; protected labels: D-V-10 | Move or remove a label. `latest` is refused (it is computed) |
| `GET /prompts/{name}/label-events` | `View` | The label history, newest first |
| `GET /prompts/{name}/metrics?from=&to=&versions=` | `View`, key `read` | Per-version metrics (D-V-17) |
| `GET /prompt-settings` · `PUT /prompt-settings` | `View` · `ManageSettings` (project admin) | The protected labels (D-V-10) |
| `POST /playground/runs` | `RunPlayground` (D-V-26) | One model run, answered as `text/event-stream` (D-V-20) |

Errors are RFC 7807 problems with the existing codes (spec 09); V adds no problem code. A missing prompt, label or version is `404 not_found`. A template that does not parse, or a version whose type differs from the prompt's, is `400 bad_request` with a field error on `template` (with the line and column, never the text). A protected label touched without the right is `403 forbidden`. A busy connection in the playground is `429 rate_limited`.

### SDK surface (both languages; spelled idiomatically)

```python
prompt = cetra.get_prompt("support-bot")                    # label "production"
prompt = cetra.get_prompt("support-bot", label="staging")
prompt = cetra.get_prompt("support-bot", version=7)
prompt = cetra.get_prompt("support-bot", fallback=FALLBACK, cache_ttl_s=60)
prompt.name, prompt.version, prompt.labels, prompt.type, prompt.config, prompt.is_fallback
prompt.variables                       # names found in the template
prompt.compile(customer="Ada", history=[{"role": "user", "content": "hi"}])
                                       # text: str; chat: list of {role, content} dicts
with cetra.context(prompt=prompt):     # every span started inside carries the link
    client.chat.completions.create(model=prompt.config["model"], messages=messages)
```

TypeScript: `await cetra.getPrompt("support-bot", { label, version, fallback, cacheTtlS })`, `prompt.compile({ … })`, `cetra.context({ prompt }, fn)`. `Client` (D-J-16) gains `client.prompts.get/list/create/createVersion/setLabel`, for scripts and CI.

### UI

- **Prompts** in the project sidebar: `/:org/:project/prompts` (list with search and label and tag filters; `?create=1` opens the New prompt dialog; admins also get the Protected labels dialog), and `/:org/:project/prompts/:prompt` with the search `tab` (`template`, `versions`, `labels`, `metrics`) and `version` (absent means latest). Creation is a dialog, never a `/prompts/new` route (D-V-32). The prompt page has these parts:
  - the version list with labels;
  - the editor, where saving writes a new version;
  - a diff of two versions;
  - label chips that the user moves or removes (protected labels show a lock and are disabled below admin);
  - the label history;
  - **Metrics**: per-version cost, latency, tokens, errors and scores (D-V-17);
  - **Traces**: a link to the traces list filtered by `prompts @> ['name@version']`;
  - **Open in playground**.
- **Playground**: `/:org/:project/playground`, opened empty, from a prompt version (`?prompt=&version=`) or from an LLM span (`?trace=&span=`). The page has:
  - a message editor with variables and placeholders;
  - JSON editors for tools and the response schema;
  - one to four model columns, each with its connection, model and parameters;
  - Run all and Run per column, with streamed output;
  - usage, cost, latency and a link to the run's trace;
  - **Save as new version**;
  - **Recent runs**: the user's playground traces.
- **Trace view**: "Open in playground" on `llm` spans, and a chip on a linked span that opens the prompt version.
- **Prompts list › Settings**: protected prompt labels (admins).

## Decisions

Options marked "(user)" were chosen by the user on 2026-11-20. The others are proposals of this design doc, for the user's review. They go into `docs/mvp-decisions.md` § Track V. Spec text is written by the milestone plans, not here.

### Registry

| # | Decision | Rejected |
|---|---|---|
| D-V-1 | **A design doc and seven milestones** (§ Milestones). M1 creates every V table in one migration. | One plan: the track crosses every crate, both SDKs and the UI. |
| D-V-2 | **Prompts belong to a project, and their names never change.** A name is 1–200 characters `[A-Za-z0-9][A-Za-z0-9_.-]*`, unique in the project, and `{name}` is the path key. There is no rename, because a rename would break deployed `get_prompt` calls and the names stored on spans. The UI offers "Duplicate as…" instead. At most 5,000 prompts per project and 10,000 versions per prompt. | Org-wide prompts (LangWatch): datasets, evaluators and keys are per project, and an `sk` key is project-bound. Folders through `a/b` names (Langfuse): a path segment that holds `/`, and route collisions (Langfuse reserves `new` and `metrics`). Ids in paths: SDK users know names. |
| D-V-3 | **Plain `{{var}}` templates, strict (user).** The only syntax is `{{ name }}`, with optional spaces, where `name` is `[A-Za-z_][A-Za-z0-9_]*`. A value is inserted verbatim and never re-parsed. Saving refuses any other `{{…}}`, `{%` or `{#` (`invalid_template`, with the position), so a template is always valid minijinja. With string values it renders the same as under D163 (except that minijinja's default drops one trailing newline), so a prompt can serve as a judge template later. A variable that has no value is an error at `compile`. There is no escape for a literal `{{`. | Full Jinja in the SDKs (user): jinja2 in Python and a JS port that differs from minijinja at the edges, against three engines in two languages. A per-version `template_format` field (Phoenix, Opik): a field with one allowed value is a placeholder (`AGENTS.md`), and a migration can add it when a second format exists. Langfuse's lenient rendering, which leaves `{{missing}}` in the output: it silently sends broken prompts to the model. |
| D-V-4 | **Rendering happens where the prompt is used.** Applications render in the SDK, so `get_prompt` plus `compile` adds no network call. The playground renders on the server with the Rust renderer. The three renderers (Rust, Python, TypeScript) pass the same cases in `fixtures/prompts/`: the template, the values, and the expected output or error. | A server render endpoint for applications: a network call on every use, and no rendering when the server is down. |
| D-V-5 | **Two types, fixed per prompt.** A `text` prompt's template is one string. A `chat` prompt's template is an array of 1–200 entries. A message is `{role, content}` with `role` `system`, `user` or `assistant` and `content` a template string. A placeholder is `{type: "placeholder", name}`. At `compile`, a placeholder takes a list of `{role, content}` messages given under its name. A missing placeholder value is an error, as for variables (D-V-3), and an empty list is allowed. A template is at most 256 KiB of JSON, with at most 100 distinct variables and placeholders. | Canonical message parts (spec 01) in the registry: SDK users pass `{role, content}` straight to provider SDKs, and a prompt has no tool results or media. The canonical format is used where messages meet spans and providers (D-V-25). |
| D-V-6 | **A JSON config on each version.** It is a JSON object of at most 64 KiB. These keys are validated: `model` (string), `connection_id` (UUID: the playground's default connection), `params` (`temperature`, `top_p`, `max_tokens`, `stop`, `presence_penalty`, `frequency_penalty`, `seed`, `reasoning_effort`, with typed ranges), `tools` (`[{name, description?, parameters}]`, where `parameters` is a JSON Schema), `tool_choice` (`auto`, `none`, `required` or a tool name), and `response_format` (`{name, schema, strict?}`). Other top-level keys are the user's own and are kept as they are. | Free-form JSON only: the playground and the UI could not trust it. A closed schema: users keep their own settings there (Langfuse, Opik). |
| D-V-7 | **Versions are integers from 1, immutable, and each has an optional commit message** (at most 500 characters). Every save is `latest_version + 1`, in one write with the label changes it asks for. Concurrent saves serialize on the prompt row, so neither gets a constraint error (Langfuse's race). A single version cannot be edited or deleted. | Content hashes as ids (Opik, which added `vN` later). Deleting versions: deployed code may pin one. |
| D-V-8 | **Labels are mutable pointers.** A label is `[a-z0-9][a-z0-9_.-]{0,63}`, never only digits (LangWatch's lesson: `2` must mean a version), and never `latest`. `latest` is computed: always the highest version, never stored and never moved. Setting a label on a version moves it off the previous one. Every move is recorded in `prompt_label_events`. A prompt has at most 50 labels. | Stored `latest`, moved on every save (Langfuse): two writers for one pointer. A pointer column on the version row (Opik's first design, which it moved out). |
| D-V-9 | **The fetch defaults to `production`.** When the label is missing, the fetch answers `404 not_found`, and the SDK falls back or raises (D-V-14). To avoid Langfuse's best-known trap (a new prompt that cannot be fetched), the UI's create and save dialogs show which version `production` points to. The create dialog has "Label as production" checked for the first version. The API never adds a label by itself. | Default to `latest` (Phoenix, Opik, MLflow): an edit in the UI would reach production without a promotion. |
| D-V-10 | **Protected labels are a per-project list, `production` by default (user).** Project admins edit the list (`PUT /prompt-settings`, at most 20 labels; a project without settings protects `production`). Moving or removing a protected label, saving a version that sets one, or deleting a prompt that carries one requires one of: a project admin (through a session or a read-write PAT), or an `sk` key with the `write` scope. Only project admins create API keys (spec 08), so a write key is a credential an admin chose to give, for example to promote a version from CI. Otherwise the answer is `403 forbidden`. | No protection by default (Langfuse): `production` is the label that matters. A fixed `production` with no setting: teams that use `prod` or `live` could not protect it. Refusing API keys: CI promotion would need a person's PAT. |
| D-V-11 | **Everything is stored in `meta.db`** (§ Tables). Prompts are small, curated and transactional, like datasets. They are not hidden by the plan data window (D175) and not touched by retention. GDPR deletion leaves them alone: they hold application text, not end-user data. A project or org drop cascades. | The columnar store: prompts are not high-volume and need transactions. |
| D-V-12 | **The fetch.** `GET /prompts/{name}/resolve` answers `{name, type, version, template, config, labels, variables, placeholders, commit_message, created_at}`, with `Cache-Control: no-cache` and a strong `ETag` of the body. An SDK revalidation with `If-None-Match` gets `304` and no body. The fetch needs the `read` key scope, which the default `sk` scopes include. An ingest-only key cannot fetch. | A separate public or prompt-only key kind: the existing scopes already express it. |
| D-V-13 | **Permissions.** Reads use `ProjectPerm::View` (a viewer, a `read` key, a read-only PAT). A new `ProjectPerm::ManagePrompts` covers creating prompts, versions and unprotected label moves, `PATCH` and `DELETE`: role `member`, key scope `write`, read-write PATs. Protected labels follow D-V-10. Writing the protected list is `ManageSettings` (project admin); reading it is `View`. `web/src/lib/roles.ts` gets the client mirrors. | Reusing `ManageEvaluation`: API keys cannot use it (D-I-24), and prompt writes from CI are a main use. |
| D-V-14 | **SDK fetch, cache and fallback.** `get_prompt` needs `init()`. Its behaviour: <ul><li>**Cache.** It caches per `(name, label or version)` in process. Version entries never expire, because versions are immutable. Label entries are fresh for `cache_ttl_s` (default 60, `0` turns the cache off). A stale entry is returned at once, and one background refresh per key revalidates it with `If-None-Match`. The cache holds at most 1,000 entries (LRU).</li><li>**First fetch.** A cache miss fetches synchronously: a 5 s timeout per attempt and 2 retries on network errors, 429 and 5xx (`Retry-After` honoured, capped at 5 s).</li><li>**Failures.** A failed refresh keeps the stale entry and logs one warning a minute, with names and status only. A failed first fetch returns the `fallback` (a text string or a chat message list; the version is null and `is_fallback` is true) when one is given, and otherwise raises `PromptNotAvailable`. This is the one call that can raise after `init()`, besides spec 10's programming errors: with no prompt and no fallback there is nothing to return. A disabled SDK (no key, D-F-3) behaves as a failed first fetch.</li><li>**Scope of the 402 pause.** The 402 pause (D-P-34) does not apply to fetches: prompts are not units.</li><li>**Amendment (M2, V2.5).** TypeScript passes the prompt to `withContext({ prompt }, fn)`. `PromptCompileError` (a missing variable or placeholder, an invalid fallback) and `PromptNotAvailable` are the prompt API's only exceptions. `compile` takes strings, numbers and booleans (`true`/`false`; an integral number renders without a fraction) and message lists for placeholders.</li></ul> | No SDK cache (Phoenix, Helicone): a round trip on every call, and an outage takes the app down. Opik's 300 s TTL: too slow a rollout for a label move. A prefetch API: the first call on each key already fills the cache. |
| D-V-15 | **Linking through the context, stored in real columns.** `cetra.context(prompt=…)` makes the context processor (spec 10) write `cetra.prompt.name` (string) and `cetra.prompt.version` (int) on every span started inside, instrumentor spans included, the same way it writes session and user. `compile()` also writes both on the current recording span. A fallback prompt writes the name only. Normalization fills these columns: <ul><li>new span columns `prompt_name` (Utf8, dictionary-encoded in Parquet, P) and `prompt_version` (Int64, P);</li><li>a new trace column `prompts` (List(Utf8), the distinct union of `name@version`, like `models`), so the traces filter is `prompts @> ['support-bot@5']`.</li></ul>These are `cetra-core` changes, which the coordinating session owns (§ Parts and crates). **Format:** a new span column changes the WAL payload schema, which spec 03 § 12 counts as a format change. Before the first public release there is no format constraint (D185), so `FORMAT_VERSION` stays 1. If M3 lands after that release, it bumps `FORMAT_VERSION` and keeps the previous reader, as § 12 requires. Columns sit after `model` (spans) and `models` (traces); a name-only span contributes nothing to `prompts`; `schema_version` 2. | Reserved metadata keys (like the experiment linkage, `metadata['cetra.experiment_id']`): every per-version metric would scan the metadata map of every span, and the trace filter would need a semi-join. | D-V-17 | **Per-version metrics come from one storage read.** `GET /prompts/{name}/metrics` aggregates, per version in the window (default: the last 7 days, capped by the plan's data window, D175), over the `llm` spans whose `prompt_name` matches: span and trace counts, error rate, cost (total and average), latency p50 and p95, average input and output tokens. Widget breakdowns do not offer prompts yet. | Precomputed rollups in `meta.db`: the store already answers group-bys over P columns. |

### Playground

| # | Decision | Rejected |
|---|---|---|
| D-V-19 | **One streaming provider layer in `cetra-eval`.** The OpenAI, Anthropic and Gemini adapters (D21, D159) generalize into a chat call. It takes the model, canonical messages, tools, tool choice, a response format, params, a timeout and a token cap, and returns a stream of events: text deltas, complete tool calls, usage, the finish reason and the response model. Each provider streams its own way: OpenAI `stream: true` with `include_usage`, Anthropic's SSE events, and Gemini `streamGenerateContent?alt=sse`. A server with no usage in its stream gives a run with no cost. The judge becomes one caller of this layer: one user message, its structured output and its answer parser. Its behaviour and its tests stay the same. The egress client gains a streaming POST with the SSRF guard (D166), the 4 MiB response cap (D159), and an idle timeout. | A second set of playground adapters next to the judge's: two copies of each provider's quirks (D-I-44, D-I-46). A provider SDK crate: none covers all three, and D21 chose hand-written HTTP. |
| D-V-20 | **Transport: SSE answering a POST, one request per model column.** `POST /playground/runs` validates the request and answers `text/event-stream` with these events: <ul><li>`start` `{trace_id}`;</li><li>`text` `{delta}`;</li><li>`tool_call` `{id, name, arguments}`, sent once the call is complete;</li><li>`done` `{finish_reason, usage, cost_usd, latency_ms, ttft_ms, output}`, where `output` is the canonical assistant message;</li><li>`error` `{class, message}`, with D160's classes and no prompt or answer text.</li></ul>A `ping` comment goes out every 15 s, as on the existing streams. Errors found before the stream starts (validation, permission, limits) are ordinary problem answers. Running four models means four requests. Each column then streams, fails and stops on its own: when the browser aborts the fetch, the server drops the provider request and records the run as cancelled. The browser reads the stream with `fetch`, because `EventSource` cannot POST. | WebSockets: a second protocol for a request-response flow. One stream multiplexing every column: cancelling one column would need a side channel. Calling providers from the browser: the keys are sealed server-side (D-I-1, D-I-4). Falling back to non-streaming with tools (Langfuse): the layer assembles tool calls itself. |
| D-V-21 | **The run request.** `{connection_id, model, messages, variables?, placeholders?, params?, tools?, tool_choice?, response_format?, source?}`. `messages` are canonical messages (spec 01), at most 200 of them and 2 MiB of body. Text parts may hold `{{var}}`, which the server renders (D-V-4) with `variables`, and a placeholder message is filled from `placeholders`. `source` is `{prompt: {name, version}}` or `{span: {trace_id, span_id}}` and is recorded on the trace only. The client sends the messages it shows, so an edited prompt runs as edited. | The server loading the prompt or span itself: the user edits before running, so the client's copy is the truth. |
| D-V-22 | **Every run is traced into the project, in the reserved environment `cetra-playground`.** One trace has one `llm` span. It holds the rendered input messages, the output, the tool definitions, the request params, the model and provider, usage, `ttft`, and the cost from the project's price table (track T). Its metadata holds `cetra.playground.run_by` (the user id) and the source. A run from a prompt version also carries `prompt_name` and `prompt_version`. It is built as OTLP and normalized like judge traces (D161), then committed in process. `cetra-playground` is treated as `cetra-eval` is: <ul><li>the SDK refuses it as an environment;</li><li>the OTLP handler rewrites it on external data;</li><li>default exclusions and online-rule strict exclusions (spec 05, D-I-9) leave it out;</li><li>a filter that names `environment` opts in (spec 05).</li></ul>One `cetra-core` test, "is this environment reserved", replaces the comparisons with `cetra-eval`. | Reusing `cetra-eval`: playground runs would mix with judge traces, and the UI could not list them on their own. No trace: no cost record, no history, nothing to link from. |
| D-V-23 | **Playground spans are not units (user).** G's usage counter skips every reserved environment, which generalizes D-I-31. The run is priced and shown, but nothing is billed: the customer pays the provider on their own connection, as D178 does for judges. With no units produced there is no units-cap check, and rule budgets (D-I-15) do not apply. Restore mode refuses runs, as it refuses every egress (D-N-25). | Counting them as units: the user's choice. |
| D-V-24 | **Limits.** <ul><li>Per user: at most 60 runs a minute and 4 at once (`429`). Per org: 16 at once.</li><li>Per connection: a run takes the connection's concurrency slot and rate token (D-I-4, D-I-6) ahead of rule jobs. Evaluation and the playground share the provider's limits. It waits at most 10 s for both, else `429 rate_limited`.</li><li>Per call: the timeout is 300 s, the most D159 allows. A stream that sends nothing for 60 s fails. `max_tokens` defaults to 4,096 when the request has none, and is at most 65,536.</li><li>The UI shows 1–4 model columns, as J's compare does (D-J-13).</li></ul> | Langfuse's 10 columns: four already fill a wide screen and four requests a click. Sharing D-I-21's limit of 10 test runs a minute: one click can send four. |
| D-V-25 | **What is sent.** Text, `tool_call` and `tool_call_response` parts, system instructions, tool definitions (`[{name, description, parameters}]`), tool choice, and a response schema. A response schema uses the connection's structured-output mode (`native`, `tool` or `prompt`, D-I-4): in `tool` mode, the forced tool's arguments are the output text. The playground shows the model's tool calls, and the user can add tool results by hand and run again. It never runs tools. Opening a span whose messages hold media or unknown parts lists those messages and refuses to run them until they are removed. | Inlining `media://` blobs as base64: per-provider media rules and size limits. Tool execution: arbitrary code or HTTP from the server. |
| D-V-26 | **Who can run.** A new `ProjectPerm::RunPlayground`: role `member`, through a session or a read-write PAT, and never an API key, because a run spends the org's provider money. The connection must be one of the project's org's (D-I-4). Viewers can open the playground and see runs, but cannot run. | Viewers running: they would spend money that admins pay for. |
| D-V-27 | **Save as a new version.** "Save as new version" writes the playground's messages and config (model, connection, params, tools, tool choice, response format) to `POST /prompts/{name}/versions`, or to a new prompt. It needs `ManagePrompts`, and D-V-10 for protected labels. Chat prompts store text messages only (D-V-5): when a message holds tool parts, the dialog names it and refuses. A run that started from a span saves literal text, and the user can turn parts of it into `{{var}}`s first. | Saving tool results into prompts: chat templates have no tool parts. |
| D-V-28 | **Playground state stays client-side.** The draft (messages, variables, columns) lives in the URL for its source and in `localStorage` per project for the edits, which is the D-C-17 pattern for browser-local state. There is no runs table: "Recent runs" lists the project's `cetra-playground` traces with `cetra.playground.run_by` equal to the user, through the existing traces list. Opening a past run puts its messages and model back into the page. | A `playground_sessions` table shared between users: no competitor needs one for the core flow, and a run is already a trace. |
| D-V-29 | **Judges stay buffered.** Judges call the layer without streaming. The layer has a buffered call that sends the same request without `stream` and decodes one JSON body into the same reply shape; judges use it, the playground streams. A judge reads the whole answer before parsing it, so streaming gains it nothing, and a streamed judge would change every request body the judge tests pin. | — |
| D-V-30 | **Stream size caps.** D159's 4 MiB applies to the answer a stream assembles (text plus tool-call arguments) and to any one SSE event; the raw stream is capped at 32 MiB. The SSE framing of a 65,536-token answer (D-V-24) is several times its text (OpenAI sends about 250 bytes per token chunk), so a 4 MiB raw cap would cut answers at about 16,000 tokens. A non-200 body is still read up to 4 MiB. | — |
| D-V-31 | **Message and parameter mapping.** System messages become the provider's system field (Anthropic `system`, Gemini `systemInstruction`; OpenAI keeps them in place). `tool` messages become OpenAI `tool` messages, Anthropic `tool_result` blocks in a user turn, and Gemini `functionResponse` parts whose name comes from the earlier call with the same id. Consecutive messages that map to the same Anthropic or Gemini role are merged. Reasoning parts are not sent; media and unknown parts, unknown roles, and tool parts in the wrong role are refused with the message index. A parameter the provider has no field for is not sent: Anthropic gets `temperature`, `top_p` and `stop`; Gemini gets all but `reasoning_effort`; OpenAI gets all. A Gemini tool call without an id gets `call_<n>`. | — |
| D-V-32 | **Registry UI.** Creation is a dialog on the list (`?create=1`), never a `/prompts/new` route, because `new` is a valid prompt name (D-V-2). The page is `/prompts/:prompt` with tabs `template`, `versions`, `labels` and `metrics` and a `version` search. Labels are set from a version row and removed from their chip (protected chips carry a lock). The diff compares a version with the previous one, line by line. Metrics windows are 24 hours, 7 days (default) and 30 days, the traces list's presets. |
| D-V-33 | **Reserved environments, one test.** `cetra_core::names::environment` gains `PLAYGROUND = "cetra-playground"`, `PLAYGROUND_EXTERNAL = "cetra-playground-external"`, `RESERVED: &[&str] = &[EVAL, PLAYGROUND]`, `is_reserved(env) -> bool` and `external_alias(env) -> Option<&'static str>`. Every place that compared with `EVAL` to hide, skip, refuse or not bill a trace uses `is_reserved`; the OTLP handler rewrites any reserved name to its `-external` alias. The judge-trace builder and the GDPR judge cascade (which find judge traces by their target) stay `EVAL`-specific. A later track adds its environment to `RESERVED` and gets every rule. | Per-place comparisons with `EVAL`: each new reserved environment would have to find every one. |
| D-V-34 | **The units rule is one function.** `crate::ingest::billable_spans(&[Span]) -> usize` counts the spans whose environment is not reserved, and `Ingest::commit` uses it. | A check in each caller: they would drift apart. |
| D-V-35 | **Interactive connection permits.** `crate::eval::interactive::acquire(state, connection, wait)` waits up to `wait` for the connection's concurrency slot (tokio's FIFO semaphore puts the waiter ahead of the dispatcher's polling `try_acquire`), then for a rate token, and returns a permit that frees the slot on drop; it fails with `Busy` at the deadline. The dispatcher and the interactive path share one `ConnectionLimit` per connection. The playground passes 10 s. | A separate limit for the playground: it would not share the provider's limits (D-V-24). |
| D-V-36 | **Playground runs and connection status.** A run uses the connection whatever its `status` (as connection tests and test runs do) and never marks it `failing`: a pause-class error is reported to the user in the `error` event only. | Marking the connection failing: one bad run would stop the rules that share it. |
| D-V-37 | **Playground request shape.** `messages` are canonical messages (spec 01) or `{type: "placeholder", name}` entries; a placeholder is replaced, in place, by the messages given under its name in `placeholders`; every `text` part of the resulting messages that came from `messages` (not from a placeholder) is rendered with `variables` (D-V-3); a missing variable or placeholder is a 400 before the stream starts. Trace ids are random. The run's trace is committed after the stream ends, also when the client cancelled (status error, message `cancelled`). Rendered text is at most 4 MiB. | — |

## Open questions for the user

- **Q1. Datasets in the playground.** Phoenix and Opik run the playground over a dataset as a server-side job that outlives the page. Doing that in cetra means a server-side experiment run, which D18 (experiments are client-side only) rules out. Should V add it (amending D18, probably as an eighth milestone), or leave it for later and keep D18 as it is? This design does neither.
- **Q2. MCP tools for prompts.** Should H's read-only MCP server (S10) gain `list_prompts` and `get_prompt`, so coding agents can read the team's prompts? It would be a small addition to M1. The design leaves it out until you say so.

## Competitors

Findings from the competitors' code (read-only), summarized from the session notes (`v-prompts-competitors.md` in the shared notes folder):

- **Templates:** Langfuse and MLflow use `{{var}}` with no logic. Langfuse leaves a missing variable as literal text. Phoenix stores a per-version format (Mustache with sections, f-string or none). Opik offers mustache, jinja2 or python. LangWatch uses Liquid. Helicone uses typed `{{hc:name:type}}`. Langfuse has a `placeholder` chat message for history.
- **Labels:** Langfuse fetches `production` by default and answers not found when nothing carries it. It sets `latest` automatically, keeps one version per label, and has the only protected labels (per project, owner and admin, while API keys may still move them). Phoenix, Opik, LangWatch and MLflow default to latest. LangWatch refuses numeric tags. Opik keeps a history of its environment pointers.
- **SDK caches:** Opik caches for 300 s with a background refresh. MLflow caches aliases for 60 s and versions forever. LangWatch caches for 5 min, or reads files synced by its CLI. Phoenix and Helicone have no cache.
- **Links:** Langfuse sets `langfuse.observation.prompt.name/version` on generations and shows median latency, tokens, cost and scores per version. LangWatch sets `langwatch.prompt.id` (`handle:version`). Opik uses a metadata list. MLflow uses a trace tag. Helicone uses request columns.
- **Playgrounds:** every one keeps provider keys on the server, except that Phoenix also accepts keys typed in the browser. Langfuse streams plain text and falls back to non-streaming with tools. Opik and LangWatch stream SSE. Phoenix uses GraphQL subscriptions. MLflow and Laminar do not stream. Langfuse allows 10 columns. Phoenix and Opik run the playground over datasets as server jobs. Langfuse, Phoenix and LangWatch open recorded spans, and Langfuse and Phoenix save back as a version.
- **Namespaces:** Langfuse and Opik are per project (Opik moved there later). Phoenix has one global namespace. LangWatch handles are unique per org, with project or org scope.
