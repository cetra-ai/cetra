# cetra — MVP definition

Name: **cetra** (cetra.sh).
Competitor research: `research/competitors.md`.

## MVP scope at a glance

**Ingestion**
- OTLP over HTTP + gRPC; normalizes OTel GenAI semconv, OpenInference, OpenLLMetry, Vercel AI SDK attributes.
- 10 MiB HTTP / 32 MiB gRPC request limit (413); attributes >8 MiB truncated with a marker.
- Server-side extraction of base64 media → content-addressed (SHA-256, per project) blobs in object storage.
- Cost + tokens from a price table (LiteLLM import + per-project custom prices, track T), incl. cache/reasoning tokens.

**Storage**
- Single binary, single machine. DataFusion + Parquet (own layout, manifest in SQLite), local disk or S3.
- WAL + in-memory Arrow buffer → spans queryable within seconds (live view).
- Tombstone deletes, physical removal at compaction; retention by dropping time partitions.

**UI** (React/TS, embedded in the binary)
- Trace list (visual filter builder + SQL-like filter DSL + full-text scan), trace tree/timeline with live updates, chat rendering of LLM spans, media rendering, sessions view, metrics dashboards: a built-in Overview and custom dashboards (D-C-16).
- SQL console over the user's project data.
- Saved views (list pages) and saved SQL queries, private or shared.
- Scores and human annotation on spans/traces/sessions.
- Datasets (versioned, CSV/JSONL import, add-from-trace), experiment results/comparison.
- Online judge rules, alert rules, settings (orgs, projects, members, API keys, LLM connections).

**Evaluation**
- Online LLM-as-judge on traces and spans: filter + sampling + cost cap; built-in templates (hallucination, relevance, toxicity, correctness vs expected, custom).
- Built-in Rust checks (exact, contains, regex, JSON valid, JSON schema, Levenshtein); webhook evaluator.
- Experiments run client-side via SDK `evaluate(dataset, task, scorers)`.

**Alerts**: error rate, cost over window, p95 latency, judge score under threshold → Slack webhook, webhook, email.

**Access**
- Orgs → projects; roles owner/admin/member/viewer (+ per-project override).
- Email/password (argon2id), GitHub/Google OAuth, generic OIDC. No SAML in v1.
- API keys: `pk-` (write-only, browser feedback) / `sk-`; SHA-256 hashed; optional expiry; ingest-only scope.
- Public end-user feedback endpoint.

**Interfaces**: REST + OpenAPI, MCP server, CLI, Python + TypeScript SDKs (thin layer over OpenTelemetry).

**GDPR**: delete by user_id, by trace/filter, by project, by org; per-project retention; cascades to all derived data.

**Packaging**: binary, Docker image, docker-compose, minimal Helm chart; documented snapshot backup.

**Cloud & plans**: the same binary self-hosted (open core, MIT, enterprise features behind a licence key) and as a cloud of cells (EU, US) with Free / Starter / Pro / Enterprise plans and a Teams add-on, billed on units through Stripe (D169–D179).

Kept after the trace-list benchmark: rebuilding the map at startup read 4 MB in 51 ms on 5M traces (`docs/research/storage/traces-benchmark.md`). |

| D91 | Query context | A2 builds the DataFusion `SessionContext`. `Storage::query` returns a `ProjectQuery`: the three raw providers (`spans`, `traces`, `scores`, stored schemas, D89), the per-query `RuntimeEnv` (memory pool, spill directory), `target_partitions` and the physical optimizer rules to append (D153). `QueryContext::new` builds the session from that: DataFusion's built-in scalar, nested, aggregate and window functions, with no table functions and no higher-order functions; no `information_schema`, no URL tables, recursive CTEs off; parser recursion limit 50, source spans collected; the hex-ID optimizer rule; only the views registered (spec 05, 03 §6). |

| D94 | Query errors | Filter, SQL and execution error messages go back to the caller (capped at 2 KiB) and are never logged; logs carry the error kind, text lengths and the duration. | D95 | Input limits | Filter DSL: at most 4 KiB and 128 operator tokens. SQL: at most 64 KiB and 512 operator tokens. Parser recursion limit 50. | D96 | SQL sandbox | One statement: a query, or a plain `EXPLAIN` of a query (no `ANALYZE`, no `VERBOSE`). Table references are unqualified names of registered views or of CTEs in scope. No table functions. Recursive CTEs are disabled. `score`, `score_label` and `has_score` are not available in SQL (D97). | D97 | Score functions | `score(name)`, `score_label(name)` and `has_score(name)` exist in the filter DSL only, on the `traces`, `spans` and `sessions` views. For each target they use the latest live score of that name (greatest `updated_at`, then greatest `score_id`). `score` is its `value_num` (null for categorical and text scores), `score_label` its `value_str`, `has_score` is true when such a score exists. Each distinct name compiles to a left join on a latest-score subquery; at most 8 distinct names per filter. `FunctionSchema` gains `in_sql` (spec 05, 09). |
| D98 | SQL results | JSON results are `{columns: [{name, type}], rows: [{column: value}], truncated}`: output column names must be unique; timestamps are RFC 3339 with 9 digits, `Z` for UTC (D64); binary is lowercase hex, maps are objects, NaN and ±inf are null; `type` is the Arrow type as DataFusion prints it. At most 10,000 rows (`limit` 1–10,000, default 10,000). `truncated: true` means more rows matched than `rows` holds, because of `limit` or the byte cap. The encoded JSON answer is at most `SQL_MAX_RESULT_BYTES` = 32 MiB: rows are taken while their estimated size fits, and the answer stops at the last row that fits. Only a first row that alone passes the cap, an encoding that passes it anyway (escapes the estimate does not count), or an encoding that does not fit the query memory pool, fails with `TooLarge` and the server answers `422 query_too_large`. A query that projects one heavy column under thousands of aliases, or cross-joins heavy rows, therefore returns the rows that fit rather than failing by the cap. Exports stream up to 10M rows and stop there (spec 05, 09). Each export chunk is at most `EXPORT_MAX_CHUNK_BYTES` = 64 MiB: an export slices every batch into pieces of at most 8 MiB estimated size, and a single row over 64 MiB ends the export as `TooLarge` (a `422` when it is the first data item, else a cut body). The estimate sizes each row as its JSON text (spec 05 § Sandbox, item 8): a string's bytes, a binary's hex length, a view's length, a nested value's children in the rows it reaches, a dictionary value by its key, a null slot as `null` whatever its key, 40 bytes per number, bool or temporal value, a decimal by its precision and scale, an interval by its display bound, and each cell's column name and punctuation. The answer's brackets and one comma per row are counted too. An alias is a cell, so it counts its values again. The estimate does not count JSON escapes; the encoder refuses output past the budget either way. |
| D99 | SQL parameters | Saved queries use `{name:Type}` placeholders, `Type` ∈ `String`, `Int`, `Float`, `Bool`, `Timestamp` (case-insensitive). Values arrive as JSON: string, integer, number, boolean; `Timestamp` takes RFC 3339 or integer epoch milliseconds. A missing, extra or ill-typed parameter is a 400 that names it. They become DataFusion `$n` placeholders before planning (spec 05, 09). |
| D100 | DSL casts | The filter DSL allows `CAST(x AS t)` and `x::t` with `t` one of `BIGINT`, `DOUBLE`, `VARCHAR`, `BOOLEAN`, `TIMESTAMP`. They compile to `TRY_CAST`, so a cast that does not fit skips the row instead of failing the query (spec 05). |

## Track A1 — Storage engine

| # | Topic | Decision |
|---|---|---|
| D-A1-1 | Compacted traces | **Compaction keeps one `traces` file per `spans` file.** Each `spans` output of a merge or day close gets its own `traces` file, computed from exactly its rows, and the `traces` files of the inputs are removed in the same commit. A day that fully merges ends with one partial per trace. A bigger day keeps one partial per trace and `spans` file, which the read-time merge already handles. Merging a whole day's partials into one file was rejected: its memory grows with the day's trace count (about 2 KB per trace), and many-source `traces` files would complicate later merges and the deletion rewrite (spec 03 §5). |
| D-A1-2 | Compaction writes | **Compaction streams each `spans` and `scores` output into a temp file** (in the target directory on local disk, `<data_dir>/tmp/compaction/` with S3), then publishes it durably, so memory stays bounded by one row group per output. `traces` outputs stay in memory. Reserving disk before a merge moves to M6 with the rest of the disk-full handling (`min_free_bytes`): it needs a free-space API that the standard library lacks (spec 03 §5, §10). |
| D-A1-3 | Covered-row predicate | **One DataFusion physical predicate decides which rows a pending deletion covers**, built from the tombstones: `spans`, `ingest_time ≤ cut-off AND (trace_id IN … OR user_id IN …)`; `scores`, the same `OR session_id IN …`; `traces` partials, `trace_id IN …` only, since a partial has no per-row ingest time. Queries, flush, compaction and the rewriter all use it, so the rule exists once. Queries filter only the files whose `deletions_applied_seq` is below a pending deletion's sequence and whose `min_ingest_time` is at or before its cut-off, and the memtable batches whose `min_ingest_time` is at or before it: a `FilterExec` over the file scan, an in-memory filter for batches. A custom `TombstoneFilterExec` was not needed. `EXPLAIN` in the SQL console prints the predicate. Trace ids of a pending deletion show until it is applied (≤ `deletion.max_delay`, accepted); user and session ids are redacted to `user_id IN (<n redacted>)` (a `Redacted` wrapper expression), so the plan never names an erased person (cross-track review X17). Once applied, storage also deletes the deletion's scope rows from `catalog.db` (spec 03 §7). |
| D-A1-4 | Deletion by session | **A `user` deletion's session IDs delete `scores` only.** Spans go by the resolved trace IDs and by `user_id`; scores by trace ID, `user_id` and session ID. A session shared with another user keeps that user's spans (spec 03 §7). |
| D-A1-5 | Deletion rewriter | **The rewriter is a compaction job kind (`rewrite`), run by a deletion pass after each compaction pass.** It shares compaction's claims, threads, merge path and commit. Each candidate file is checked with a pushed-down scan (statistics and bloom filters, `LIMIT 1`): a file with a covered row is rewritten at its own level, a clean one gets its `deletions_applied_seq` raised in a catalog edit without a rewrite. A pending deletion older than `deletion.max_delay` is logged once as a warning (spec 03 §7). |
| D-A1-6 | Media | **`put_media` verifies the SHA-256 of the bytes and refreshes `last_seen_at` on every call; media GC keeps blobs seen in the last hour and runs daily and for a project as soon as one of its deletions is applied.** The guard counts from the last `put_media` instead of the first, so a reused blob is never collected under new spans, and one hour covers the gap between a blob's put and its span's append. Running on deletion keeps media within `deletion.max_delay` too. On S3 a blob is a plain `PutObject`: its name is its hash, so an overwrite writes the same bytes and no conditional put is needed (spec 03 §9). |
| D-A1-7 | Project drop | **Appends to a dropped project fail with `AppendError::ProjectDropped`.** `drop_project` holds new appends while it commits; the commit obsoletes the project's files (GC deletes them), records it in `projects`, removes its watermark and marks its pending deletions applied; then its media is deleted. The committer refuses files of a dropped project, and files older than a retention watermark, so a flush or compaction prepared earlier cannot bring data back (spec 03 §4, §7, §8). |
| D-A1-8 | Query admission | **Each query gets a memory pool of its own over one process-wide pool, and `Storage::query` admits it by taking `query.initial_memory` (64 MiB) first.** It waits up to `query.admission_wait` for those bytes, then fails as busy (503). Past them the query grows from the shared pool up to `query.max_memory`; when it can't, sorts and spillable aggregates spill and other operators fail the query as too large (422). Many small queries run at once, which fixed 2 GiB slots would not allow; a query that loses memory to others mid-run fails as too large rather than waiting. Compaction keeps its own pool (spec 03 §6). |
| D-A1-9 | Disk full | **Free disk is measured every second; under `storage.min_free_bytes` the appends and `put_media` fail with `DiskFull` (503), and every compaction job reserves its input size first, in both modes, and is deferred when it doesn't fit.** S3 mode reserves too because compaction outputs stream through a local temp file in both modes. A job that doesn't fit is retried by a later pass instead of waiting, so it holds its input claims only until it fails and doesn't block rewrites of those files (spec 03 §5, §10). |
| D-A1-10 | Quarantine | **Files a failing read touched become suspects; a verify pass re-reads each whole from the object store and quarantines the corrupt ones.** Suspects come from compaction, the deletion check, the anchor rebuild, the media GC and failed queries (every file the query scanned), so a corrupt file compaction never touches again is still caught. A corrupt `spans` file goes with its `traces` file; a corrupt `traces` file is rebuilt from its `spans` file instead. Quarantined files are kept for inspection until retention, a project drop or a pending deletion that may cover them retires them. There is no periodic scrub (spec 03 §10). |
| D-A1-11 | S3 read cache | **A cache store wraps the S3 store and serves data-file ranges from 1 MiB blocks on local disk, each with a CRC-32C, kept across restarts.** Blocks rather than exact ranges, so different queries over the same pages share entries. Flush and compaction write their outputs through; GC deletes drop blocks; verification bypasses the cache. The cache never writes under twice the disk floor (spec 03 §6). |
| D-A1-12 | Benchmarks | **Benchmarks are `#[ignore]` integration tests run by hand in release mode, with results in `docs/research/storage/benchmarks.md`.** No criterion micro-benchmarks and no `tools/bench-storage` crate: the engine's internals are crate-private, and spec 03's capacity check is about end-to-end numbers. The S3 runs use the Versity Gateway documented in `crates/storage/tests/s3.rs`. |
| D-A1-13 | Range-mode `traces` memory | **`TracesExec` sorts each hash partition by `trace_id` and merges one run of partials at a time; within a query, each operator that can spill gets a fair share of `query.max_memory`.** The hash merge held every trace of its window, at ~2.2 KB per trace whatever the columns (29 accumulator slots of 72 bytes), so every range-mode query, `count(*)` included, failed at the default 2 GiB above ~850k traces (M6.6 finding). The sort is DataFusion's `SortExec`, which spills; the merge holds at most 1,024 sorted partials' traces. Results are unchanged (the merge rules don't depend on input order), and at 1M traces the sorted merge was 1.8–3.6× faster with 3–8× less peak memory. Fair shares (DataFusion's `FairSpillPool` rule) are needed because with a greedy pool one partition's sort starved the others and a sort can only spill its own memory. Rejected: a higher default (only moves the limit: ~12 GB at 5M traces); one accumulator slot per merged column (3–8× for narrow queries, still linear; kept as a later optimization); finer hash partitions (all run at once, same total); spilling the hash merge (a merged trace isn't a valid partial, so it needs its own state format); a time-ordered merge with a `trace_lookback` watermark (splits traces with partials more than 1 h apart into two rows). Spill disk is not capped by `min_free_bytes` (D-A1-9); that is a separate follow-up. Plan: `plans/a1-storage/13-m6c-traces-merge-memory.md`. |
| D-A1-14 | WAL rotation after each flush | **Every committed flush asks the writer to start a new segment when the open one holds records, and truncation then deletes every segment whose records are all flushed; a segment that also holds newer records goes at the next flush. The writer syncs the old segment first when it holds unsynced bytes, then creates the new one and fsyncs its directory entry; if the new file exists but its creation failed, the writer removes it (or stops, when it cannot), so truncation never mistakes it for a later segment.** A deleted row's WAL bytes then leave by the end of the flush cycle after they were written (minutes at low traffic), not when the segment reaches 64 MiB, so a deletion's erasure covers the WAL too. The rotation is best effort: a failure is logged and the drained segment waits for the next flush, and the writer keeps going. A clean shutdown does not rotate, since the writers stop before the final flush; the drained segment waits for the first flush after the next start. Spec 03 §1, §7. |

## Track A2 — Query layer

| # | Topic | Decision |
|---|---|---|
| D-A2-1 | SQL statement caps | **Every token or keyword that sqlparser chains left-deep counts as an operator token (D95): set operations, `AT`, `COLLATE`, subscripts, `:`, `#`, the PostgreSQL `~~` family, `#-`, `@?`, `^@`, `RLIKE`, `REGEXP`, `MATCH`, `MEMBER`, `OVERLAPS` and `OPERATOR`. Pipe syntax (`\|>`) is rejected, and a SQL console statement reads at most 32 tables** (each view, CTE reference, derived table or `UNNEST` in a `FROM` or `JOIN`, and each `INTERSECT` or `EXCEPT`). sqlparser builds these chains without using its recursion limit, and DataFusion then overflows a 2 MiB stack while planning them: about 2,600 `UNION ALL` terms, 1,000 `INTERSECT` terms, 2,600 `AT TIME ZONE` terms or 700 joined tables in a release build, and 1,000 subscripts, 4,000 pipe stages or 2,000 `~~` in a debug build. That aborts the process. `INTERSECT` and `EXCEPT` run as joins, and a chain of them overflows when it runs from about 384 terms (debug and release), well under the operator limit, so each counts as a table. 32 tables also bound planning time: join planning grows superlinearly (about 4 s at 128 tables, over 10 minutes at 512) and the request timeout cannot interrupt it (spec 05 § Sandbox). |
| D-A2-2 | Guarded scalar functions | **The SQL console's session (D96) leaves out the scalar functions whose result can be far larger than their arguments or that read storage internals (`range`, `generate_series`, `repeat`, `lpad`, `rpad`, `replace`, `regexp_replace`, `array_repeat`, `array_resize`, `array_replace*`, their `list_*` aliases, `levenshtein`, `input_file_name`, `file_row_index`), and wraps every other scalar function except `get_field` so each call reserves the bytes it reads in the query memory pool, failing with `query_too_large` when the pool is full.** DataFusion's pool only sees operators that reserve memory; the arrays a scalar function returns are invisible to it, so `repeat('x', 4e8)` used 1.6 GB under a 64 MiB pool. The reservation lasts for the call only (a peak check). For every function left in, the output is at most a small multiple of what is counted; `concat_ws` and `array_to_string` count their separator once per place it is written. `get_field` stays unwrapped: it only extracts from its input, and DataFusion recognises it by type for pushdowns. The encoded-size caps of D98 (`SQL_MAX_RESULT_BYTES`, `EXPORT_MAX_CHUNK_BYTES`) bound what the console encodes and returns: each batch is sized row by row as it is pulled, so projecting one column under many aliases fails by the cap. They do not bound the memory a DataFusion operator uses to build one batch. Literal broadcast and join row duplication (a cross join's `take`) stay outside the pool, and their remaining bound is one output batch of 8,192 rows times the payload size. ClickHouse-based competitors get the equivalent from ClickHouse's allocator-level `max_memory_usage`; DataFusion has none. The reservation competes with the query's own operators in its pool, capped at `query.max_memory` (A1 M6.1) (spec 05 § Sandbox). A last optimizer rule swaps planner-built functions for their guarded twins and turns `a || b` on strings into a guarded call of DataFusion's own `||` kernel, so concatenation chained through CTEs cannot double memory past the pool either. |
| D-A2-3 | Automatic buckets | **`bucket=auto` over more than 2,000 daily buckets is a 400 with the explicit-bucket message (`too many buckets; pick a wider bucket`).** Without the cap a window of `[0, i64::MAX)` makes about 106,750 daily buckets, and the dashboard allocates a point per bucket for every series and group, outside the memory pool and the timeout (spec 05 § Dashboard metrics). |
| D-A2-4 | Exact cost sums | **A trace's `cost_total` is merged in integer units of 1e-18 USD, and session and user totals, the dashboard's cost KPIs and cost series (total, by model, top models, evaluation), and the alert cost value, are summed as `Decimal128(38, 18)`.** Floating-point addition is not associative, so an `f64` sum depended on the order partials or rows arrived in (hash repartitioning, file grouping, partitioned aggregation). A cursor on a cost sort stores the exact value, and the next page then repeated or skipped the boundary row when the recomputed sum moved by one ulp. Integer and decimal sums are exact, so the order no longer matters. The range (±1e20 USD) is far past any real total; the per-value rounding (5e-19 USD) is invisible. A non-finite or out-of-range trace cost, which B1 never produces, fails session, user, dashboard and alert queries (`query_failed`) instead of being skipped (spec 01 § Traces, spec 05). |
| D-A2-5 | CSV formula guard | **A CSV export writes a string cell or header name that starts with `=`, `+`, `-`, `@`, tab or CR with a leading `'`, so a spreadsheet shows it as text instead of running it.** Span text comes from instrumented applications and their end users (prompts, metadata, ids), and an export opened in Excel, LibreOffice or Google Sheets could otherwise run a formula that reads neighbouring cells. The rule is the OWASP one. It is lossy and CSV-only: numbers (a negative one stays `-1`), bools, nulls and JSON arrays and objects are written as before, and NDJSON and Parquet stay exact (spec 05 § Sandbox item 8). |
