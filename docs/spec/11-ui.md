# 11 — Web UI

Vite + React + TypeScript, TanStack Router (file routes, typed search params) + TanStack Query + TanStack Table (virtualized with TanStack Virtual), shadcn/ui + Tailwind, Inter for text and JetBrains Mono for IDs, numbers, JSON and code (D127), Recharts through shadcn `chart` for charts (D128), CodeMirror 6 for SQL/DSL editors (with schema-driven autocomplete), Shiki-free JSON viewer (custom collapsible tree). API client: `openapi-typescript` types generated from `crates/server/openapi.json` (committed as `web/src/api/schema.gen.ts`, checked up to date) with `openapi-fetch` + `openapi-react-query` (D75). Lint/format with Biome, tests with Vitest + Testing Library (D74). In development (`pnpm dev`) and in tests, Mock Service Worker answers the API from `fixtures/api/` (D76); `pnpm dev:server` proxies `/api` and `/v1` to a running `cetra` on port 8080 instead. Mocks are never part of the production build. Built output embedded in the binary by the `cetra-ui` crate (gzip precompressed, ETags, SPA fallback; D-G-35). Every path that is not a file serves the app, including ids with a dot such as an email address. Dark by default; light and system stay selectable (D127).

**State in the URL:** time range, filter expression, search, sort, columns, selected trace/span and the trace mode are all search params, so every view is shareable and bookmarkable.

A project slug is never `settings` (the server refuses it, spec 09), so `/:org/settings/*` always reaches the org pages and no project's `/:org/:project/…` URL is shadowed by them.

Command palette (⌘K): jump to project/page, paste a trace ID to open it.

**Saved views** (traces, spans, sessions, users lists): a "Views" dropdown — save, save as (with "Share with project" and "Make my default"), rename, delete, set as my default / unset default, and discard changes; the actions that change a view apply to views you own, and there is no project-wide default (D186). Loading a view replaces the URL params; a "modified" dot appears when the current state differs from the loaded view. The default view applies when a list page is entered with no search params: when the page loads, or from the sidebar, ⌘K or a `g` shortcut. A change made on the page that leaves the search empty does not re-apply it (D-C-2).

**Signed out (D-L-1).** The root route's `beforeLoad` loads `GET /api/auth/me` for every non-public route. A `401` redirects to `/login?redirect=<path and search>`, or to `/setup` while the server needs setup. A `401` from `/api/v1/*` or from `GET /api/auth/me` during use does the same and clears the query cache. `/login` shows the providers of `GET /api/auth/config` as "Continue with …" buttons, the password form when password login is on, and the message for an OAuth `?error=` code (spec 08). When password login is off, `sso_discovery` is false and exactly one provider is configured, `/login` leaves at once for that provider with its `?redirect=` (location replaced, so Back does not return to it), except on `?password=1`, `?error=` and `?signed_out=1` (R7, D-S-5). Under the same condition, the invite page sends a visitor without a session to the provider with `redirect` back to the invite, so an invitee without an account signs up there and comes back to click "Join"; not when sign-up is `disabled` and the email has no account, and not after the visitor signed out of another account on that page (R7, D-S-7). Sign-out lands on `/login` with the `signed_out` flag (written `?signed_out=true`), which says "You're signed out." and never leaves at once, since the provider would sign the user straight back in (D-S-6). With password login off, the page links to `/login?password=1` ("Instance admin? Sign in with a password"), which shows the password form for instance admins (D-S-4); the reset page accepts a reset link, and the account page shows the password section, for instance admins only.

**Demo org (D187).** `GET /api/auth/me` marks the instance's demo org with `demo: true` and lists it last. The org switcher shows it last, after a separator, with a "Demo" badge. `/` opens the first org that is not the demo, and the demo only when the user has no other org. `/demo` opens the demo org's first project (by name), or `/` when no org is the demo; the website's "Try demo" link points there, and a signed-out visitor goes through `/login?redirect=/demo` like any page. In the demo org, a user whose role there is `viewer` sees a thin banner under the top bar: "You're exploring the cetra demo, read-only." with a link "Send your own traces" to `/` (their own org). Controls above the viewer role are disabled with the usual reason (D-L-4); the dashboards of a demo-org viewer follow § Dashboard → Demo org.

**Login with org SSO (track P's M5).** When `sso_discovery` is on, the login page asks for the email first, posts it to `/api/auth/sso/discover`, and sends emails of an SSO domain to their org's identity provider; other emails get the password form and the instance providers. `/login?password=1` skips the email step and shows the password form even when password login is off (instance admins, D-P-58, D-P-60, D-S-4). An org sign-in that found no seat lands on `/sso/no-seat?org=<slug>`, which says so and links to `/` (D-P-56); an `org` that is not slug-shaped shows the generic text.

**Roles (D-L-4).** Settings pages the caller's role cannot use are left out of the settings nav, and show a Forbidden state when opened by URL. Actions above the role are disabled with the reason in a tooltip. **Secrets (D-L-5)** are shown once, in a dialog that closes only on "Done", or on Esc and outside clicks after a Copy.

## Layout and density

A thin top bar and a collapsible left sidebar (D124, D-C-12). The bar is a breadcrumb (D-C-20): the product mark and name, the org and the project (each a switcher shown as text with a chevron), then, on a project page, the page name as the page's only top-level heading (plain text; item pages such as a new or edited rule use a second-level heading), and, on pages with an open item, `›` and the item. On the dashboard the item is the dashboard switcher; on Traces, Spans, Sessions and Users it is the saved-views menu; on a dataset, a prompt, an evaluator, a user or a session page it is the item's name (a session's id). Page toolbars have no title of their own. On the right, inside a project: the ingestion dot (green "Receiving spans" when `last_ingest_at` is less than 5 minutes old, grey otherwise; its tooltip says when spans last arrived, or that none arrived since the server started; it links to Traces), then, while at least one enabled alert rule is firing, a bell with their count whose popover lists them (name, when it last fired, a link to the rule) with "All alerts"; then ⌘K ("Search or jump to…"). On pages without the project sidebar (org, account, admin and settings pages) the bar also shows the theme toggle and the user menu.

The project sidebar groups the project pages under small muted headings: **Observe** (Dashboard, Traces, Spans, Sessions, Users), **Monitor** (Alerts, Issues), **Evaluate** (Prompts, Playground, Evaluators, Online rules, Issue sources, Annotation queues, Datasets, Experiments) and **Explore** (SQL). Each item's tooltip shows its `g` shortcut. Three items carry a live badge, read from the list query their page makes (same cache entry) and refreshed every minute (experiments every 30 s): a red count of firing alert rules on Alerts, a warning dot on Online rules when a rule is paused on errors, and a count of running experiments on Experiments. Only the first page of each list (100 rows) counts. Below the pages, **Recent** lists the last five traces, sessions, evaluators, datasets and experiments opened in the project, each with its kind's icon and its name (the id until the name is known); the list is stored per project in localStorage, together with the ⌘K palette's recent traces. The footer holds Theme (a menu with mode, palette and density), Settings, the account button (avatar, name and email; its menu has Account, Admin for instance admins, Show times in UTC, and Sign out), a Docs link and the version.

The sidebar collapses to icons, with its toggle at the far left of the top bar (before the product mark, in the same place open or collapsed) or ⌘B / Ctrl+B. Collapsed, every item has a tooltip, section headings become dividers, badges become dots on the icon, and Recent is hidden. The choice is stored in localStorage; below 1024 px wide the sidebar starts collapsed without changing the stored choice, and below 768 px it becomes a sheet opened by the same toggle.

Base text is 13 px. Text uses a named scale only: caption 11 px, body 12 px, UI 13 px, title 15 px, heading 18 px, display 24 px (D-C-11). The theme menu's density, Compact (default) or Comfortable (14 px base, each size +1 px, 32 px rows), is stored per browser. Table rows are a fixed 28 px in Compact and a single line; previews are truncated and shown in full on hover. IDs and numbers use JetBrains Mono (D127). The theme is dark by default; light and system stay selectable. The theme menu also picks a colour palette (D-C-9): GitHub (default), Colour-blind, High contrast, Tokyo Night or Nord, stored per browser like the theme.

Times display in the local time zone. "Show times in UTC" is a user-menu setting stored in localStorage. Hovering a time, and copying it, uses the full RFC 3339 timestamp with nanoseconds (D130).

## Pages

### Filter bar

The text is the truth (D129). One single-line CodeMirror editor holds the filter DSL (spec 05). A client parser splits top-level `AND` conjuncts and recognises simple shapes as editable chips: `column op literal`, `IS [NOT] NULL`, `[NOT] IN (…)`, `@>`, `score('n') op x` and `has_score('n')`. Anything else is a raw chip. A filter with a top-level `OR` is one raw chip, because `AND` binds tighter and splitting it would change its meaning. The `AND` of a `BETWEEN` is never a split point. Click-to-filter puts a filter with a top-level `OR` in parentheses before appending `AND` (D-C-1). The server is the validator: a `400 invalid_filter` underlines the reported position and shows the message, and a broken filter is never applied silently. Autocomplete comes from `GET /schema` for columns and operators, and from `GET /facets` (05 § Facets) for values: in a value position after `field =` or `field !=`, inside `IN (` or `NOT IN (`, or inside `@> [` for a list field, it offers the field's values over the list's window and flags, with their counts. The chips wrap. A "+ Filter" button opens the chip editor empty; its field picker is searchable, its value input suggests values from `GET /facets`, and `IN`/`NOT IN` values are edited as tokens.

**Filter row** (D-C-13): list toolbars have a second row under the first: a "Filters" toggle with the number of top-level conjuncts, the preset chips, then the filter bar. The dashboard's row 2 holds only its filter bar and group-by.

**Facet sidebar** (D-C-13): on Traces, Spans, Sessions and Users, a 240px panel left of the list (open by default; `cetra.facets.open` in localStorage) with "Search filters" and one collapsible section per field (expanded set per view in `cetra.facets.<view>.expanded`); a collapsed section fetches nothing. Value sections have Select and Text tabs: Select lists values with counts and checkboxes, a value search, a "(none)" row, "Show more" (up to 50) and a hover Exclude; Text writes `ILIKE` or `NOT ILIKE` patterns. Trace ID is a text section; map columns list their keys, and a key opens a values section for `map['key']`; number fields show a histogram with p50/p95/p99, bars that select a range (shift-click extends) and min/max inputs. Selections are written into the filter text, which stays the truth: one value is `f = 'v'`, several `f IN (…)`, excluded ones `!=`/`NOT IN`, "(none)" `IS NULL`, list fields `f @> […]` (rows with all selected values), ranges `f >= lo AND f < hi`. A section owns the simple chips on its field; other conjuncts keep their text and order. With more than one owned chip it shows "Edited as text" and only Clear. Counts are fetched with the filter minus the section's own chips, so the other values stay visible. On Users the counts are traces. A list fixes "now" when it opens, so coming back to one asks for a later window: until that answer arrives, a section shows the latest cached answer for the same view, field, filter, switches and window length instead of a loading state.

**Presets** (D-C-13): toggle chips in row 2. Traces and Users: Errors (`status = 'error'`), Slow (`duration_ms >=` the window's p95), Expensive (`cost_total >=` the p95), Has score (a menu of score names, `has_score('n')`). Spans: Errors, Slow, Expensive and LLM (`span_kind = 'llm'`). Sessions: Errors (`error_count > 0`), Slow, Expensive. The p95 comes from `GET /facets` over the window and flags without the filter, rounded to 3 significant digits; Slow and Expensive are on while a lower bound on their field exists.

**Filters kept across lists** (D-C-14): each list page writes its range, flags and filter to sessionStorage (`cetra.list-context.<org>/<project>`). Entering another list page with empty URL search params and no default view applies them: range and flags always, and the conjuncts whose columns mean the same in both views (Traces ↔ Users: all; otherwise `session_id`, `user_id`, `environment`, `release`, `tags`, `metadata`, `trace_id`, restricted to `user_id` and `tags` for Sessions; never score calls). A notice says "Filters kept from <list>", with how many were not kept, and Clear.

**Cell menu**: right-clicking a filterable cell (traces name, status, models, environment, session, user; spans name, kind, status, model, provider, session, user; sessions user; users user ID) offers Filter (`=`, or `@>` for lists), Exclude (`!=`), Copy value, and Open session / Open user for those IDs. The hover "+" stays.

### Traces (list)

- Header: **saved views menu**, time-range picker (presets `15m` / `1h` / `6h` / `24h` / `7d` / `30d`, default `24h`, plus a custom `from` and `to`; a typed duration such as `2h` becomes an absolute `from` and `to`, D186; "live" toggle), filter bar, search box, columns menu, an "Include" menu with "Evaluation traces" and "Experiment traces" (both off by default; the button shows how many are on, D-C-15). Presets and custom ranges older than the org's data window (`data_access_days`) show a lock and "available on a paid plan" with the Upgrade button, and are not applied; a link to a hidden trace is a plain 404 (D-P-48).
- Histogram above the table: traces per bucket over the list's range, filter and flags, stacked as OK (`status <> 'error'`) and errors (`status = 'error'`), drawn from the widget query (D-C-16). Dragging across buckets selects that range.
- Table (virtualized, infinite scroll by cursor): status dot, start time, name, input preview, output preview, duration, tokens, cost, models, session, user, tags, scores (one column per score name present, toggleable), environment.
- Live mode (`live=1`, D134): subscribes to `/traces/stream` when the range is a preset and the sort is `start_time` descending. An absolute range or another sort disables the toggle. The stream gets the list's `filter`, `search`, `include_eval` and `include_experiments` (D-C-5). New rows slide in with a highlight at their start-time place, since traces arrive in the order they finish (a row older than every loaded one waits for paging while more pages remain); a known id is replaced in place. Scrolling away from the top buffers arrivals behind a "N new traces" pill. The buffer keeps the newest 500; past that the pill reads "500+ new traces" and revealing it refetches the first page. A live insert that would grow the first page past 500 rows refetches it instead (D-C-4). At most one first-page refetch runs at a time; triggers during it queue one more refetch after it (D-C-4). A status dot beside the toggle shows connecting, open or retrying, with that word as its name. A stream that fails before it opens is probed once: a 401 goes to `/login` (D-L-1), other 4xx except 408 and 429 stop the stream (status closed), and network errors, 5xx, 408 and 429 retry with backoff capped at 30 s. The list opens no stream until its first page loads, and none while the list failed to load; a failed background refetch keeps an open stream.
- Row click opens the trace beside the list and sets `?trace=<id>` (D125). The list keeps its scroll and its selection. `j`/`k` or `↑`/`↓` move between rows and the open trace follows; `Enter` activates the focused row; `Esc` closes the trace. The same view is the full page at `/:org/:project/traces/:traceId`.
- **Layout** (D-C-6): a switcher in the list toolbar, and another in the open trace's header, picks one of four layouts. The choice is a per-browser preference in localStorage (`cetra.list_layout`, default `split`), shared by the Traces and Spans lists, and it is not in the URL or in saved views. **Split** (default) is a resizable horizontal split: the list on the left (40%), the trace on the right. **Drawer** keeps the list at full width and shows the trace as a non-modal panel over the right 70% (30% to 95%, dragged from its left edge or with the arrow keys; stored as `cetra.split.traces.drawer`); the list stays clickable and `Esc` closes the panel (D-C-7). **Rail** shrinks the list to a narrow strip with fixed columns (Start, Name, Duration) and, while a trace is open, a compact toolbar with only the title (D-C-8). **Bottom** is a vertical resizable split: the list on top (40%), the trace below (60%). Each mode keeps its own ratio in localStorage: `cetra.split.traces`, `cetra.split.traces.rail` and `cetra.split.traces.bottom`. Spans use the same ratios.
- "Delete matching…" (admins, track M): deletes what the list shows (filter, search, range, toggles) after a count preview, "Delete N traces"; more than 100,000 matches must be narrowed first (D-M-5). Checked trace rows can be added to a dataset in bulk, up to 100 at once (D-J-25); export CSV waits for its API contract (own plan; D123). Checked rows can also go to an annotation queue ("Add N to queue"), and the list's filter with "Add matching to queue…" (§ Annotation queues).
- Empty state: onboarding snippets (OTel env vars, Python, TS, Vercel AI SDK) with the project's key prefix, shown when the project has no trace at all: an empty list with no filter, search, custom range or eval/experiment toggle sends one `limit=1` request over all time (no window, no filter; eval and experiment traces excluded). Only when that answers no rows does onboarding show, and it polls the list every 5 s. Otherwise the list is empty with the message "No traces in this time range." and the range control visible; a constrained list shows "No traces match" with "Clear filters".
- URL search params: `range` (or `from` and `to`, RFC 3339, both or neither, `from < to`; the pair wins over `range`); `filter` (DSL text); `search`; `sort` (`TraceSort`, default `start_time`); `order` (`asc` or `desc`, default `desc`); `eval` and `exp` (`1` when on, otherwise off); `cols` (comma-separated column ids); `view` (saved view id); `trace` (32 lowercase hex); `span` (16 lowercase hex); `mode` (`tree` or `transcript`, default `tree`); `live` (`1` when on). An invalid value is dropped.

### Spans (list)

The same table, filter bar and layout switcher as Traces, with the same four layouts and preference, over `GET /spans` (D133). Rail shows Kind, Name and Duration. One row per span. There is no spans-first default. URL search params match the traces list except `sort` is `SpanSort` (default `start_time`) and there is no `mode` or `live`: `range` or `from` and `to`, `filter`, `search`, `sort`, `order`, `eval`, `exp`, `cols`, `view`, `trace`, `span`. `?trace=` and `?span=` open that trace with the span selected. Checked rows and the filter can be added to an annotation queue, as on the Traces list.

### Trace view

- **Left:** a span tree with three modes (D-C-10). **Tree** (`mode=tree`, the default): each virtualized row has an indented name, a kind icon and status, and right-aligned duration, tokens and cost. **Timeline** (`mode=timeline`): the same rows plus a bar on a shared time axis, with zoom (D126). The grid has one set of rows, one selection and one scroll. Error spans are red; rows are collapsible; a search runs within the tree. A **Transcript** toggle (`mode=transcript`) shows the trace's LLM and tool spans in order as one conversation. In Transcript mode the right panel shows a trace summary (totals, scores, the root's question and final answer, failed spans) until a block is picked; a "Trace summary" button returns to it, and the picked block is highlighted. Each LLM turn shows only the messages not already in the previous LLM call; it waits for that call's detail and, if it cannot be loaded, shows the full input with "Earlier context could not be loaded". Live: when the trace ended within the last 10 minutes, or the list is in live mode, the view subscribes to `/traces/:id/stream`, inserts spans in tree order, and shows a Live badge with the connection status and a Stop button. The timeline window follows new spans until the user zooms.
- **Right (selected span):** header (kind, name, model, provider, duration, TTFT, tokens breakdown incl. cache/reasoning, cost, status) and tabs:
  - *Chat* (for `messages` format): system instructions collapsed, messages as bubbles, tool calls/results as cards, reasoning collapsed, images/audio/PDF rendered from `media://` refs, tool definitions in a drawer.
  - *Input / Output*: JSON tree / text / raw toggle; copy buttons; "truncated at ingest" badge when applicable.
  - *Attributes*: metadata, attributes, resource attributes, events (exceptions with stack traces), links.
  - *Scores*: the span's and the trace's scores (name, value, source, reason, author), read-only; an evaluator score whose metadata has `judge.trace_id` links to that trace ("View judge trace").
  - *Annotate* (D-I-26, D-I-37): a form built from the project's live score definitions, one control per definition (a number within its range, Yes/No, one of the categories, or text) with an optional reason. A Trace/Span switch picks the target (the trace by default). It shows and edits only the caller's own `human` scores: Save writes the changed rows in one `POST /scores` without `score_id` (so each annotator keeps one score per name and target), and Clear deletes the caller's own score. Trace and span annotations carry the trace's session and user ids. Viewers see "Only members can annotate."; with no definitions, the tab links members to Score definitions. Another member's `human` score can be changed only by a project admin, through the API (D-I-36). Opened from an annotation queue, the form shows only the queue's live definitions and saves with the queue's `queue_id` (§ Annotation queues).
- Inside the trace view, the tree and the span detail are a second resizable split (D125). The tree pane defaults to 40% in Tree and Transcript and to 60% in Timeline; each ratio is in localStorage.
- Trace header: name, total duration/cost/tokens, session (link), user (link), tags, environment, release. Actions now: copy link, copy ID. "Delete trace" (admins, plain confirmation; track M). Actions: Run evaluator (track I) and Add to dataset (track J, D-J-8): one dialog for the trace root or the selected span, input and output prefilled and editable, into an existing or a new dataset. **Add to queue** (track AQ) adds the trace, or the selected span, to an annotation queue of the same kind; an "In n queues" chip links to the queues that hold the trace.

### Sessions

List (session, first message, start, last activity as relative time, trace count, user, duration, tokens, cost, errors, error rate, scores; last answer and tags hidden by default; inline bars on traces, tokens and cost), with a summary strip (sessions, average turns and duration, error rate, cost, tokens) and a "Sessions started" chart computed from the loaded rows, and detail: a **chat transcript** reconstructed from each trace's root input/output in order, shown as chat bubbles (the user's input, the assistant's answer, rendered as Markdown) with a meta line per turn and a menu for copying and for the full details; picking a turn opens its trace beside the conversation, with the tree on top and the span detail below; session-level scores. The list's URL search params are `range` or `from` and `to`, `filter`, `sort` (`SessionSort`, default `start_time`), `order` (default `desc`), `eval`, `exp`, `cols` and `view`. The session page takes `trace`, `eval` and `exp`. Its split defaults to 55% for the conversation. The header's **Annotate** button opens the same form on the session in a side sheet (members and above; D-I-37). The header also has **Add to queue** and the "In n queues" chip (§ Annotation queues).

### Users

End users list (traces, sessions, cost, last seen, errors) and per-user page (their sessions, totals). URL search params are `range` or `from` and `to`, `filter`, `sort` (`UserSort`, default `last_seen`), `order` (default `desc`), `eval`, `exp`, `cols` and `view`. GDPR action "Delete user data…" (admins; type the user ID to confirm; track M, D-M-12).

A user's identity comes from their `user.*` metadata: `name` (shown with the ID after it, else the ID alone), `plan` (a coloured pill) and `email` (drawer and page headers). ### Dashboard

`/dashboard` shows the project's **Overview** (the built-in preset until a member saves a change to it, D-C-18); `/dashboard/:dashboardId` shows a custom dashboard (D-C-16). The header holds a dashboard switcher (Overview first, then the project's dashboards by name, then "New dashboard", whose dialog asks for a name, a description and what to start from: Blank, or one of the templates Cost, Latency, Quality and Coding agents (D-CA-11), whose widgets are copied into the new dashboard and are then its own, D-C-21), the time range picker and, for members on a custom dashboard, "Edit" and a menu with Rename, Duplicate and Delete. On the Overview, members get "Edit" and a menu with Duplicate and, once the project has its own copy, "Reset to default" (after a confirmation it deletes the copy and shows the preset again); it cannot be renamed or deleted. A duplicate is a new custom dashboard with the same widgets. Viewers and API keys get no editing controls.

**Widgets.** Every chart is a widget query (05 § Dashboard queries) drawn as a line, bar, area, horizontal bar, number or table, or a heading. The dashboard's filter bar, group-by and "Include" menu apply to every widget; a widget's own filter adds to them. The UI asks for an explicit bucket width, the smallest giving at most 60 buckets over the range. Axes use round ticks: times on round boundaries in the shown time zone, values in steps of 1, 2 or 5, durations in one unit per axis. Values are formatted by their field: durations, USD for costs, percentages for rates, counts otherwise. Colours carry meaning: a measure whose `where` is `status = 'error'` uses the error colour, and a model keeps one colour across widgets (by the cost ranking of the range, as the top models). A widget with no data is a short line with the reason; a widget whose query fails shows the error and a retry. Number widgets ignore the dashboard's group-by (they always show the total) and show the value, a sparkline and the change against the previous period of the same length: `new` when that period is zero, `×N` from a 500 % change, else a percentage, with its tooltip giving the previous value. Tables list the groups with one column per measure. Line charts with `split` draw one small chart per group (at most 6). Bars with `fade_below` fade the buckets with fewer rows.

**Overview.** The built-in preset is a fixed set of widgets defined in the UI, in this order, with no headings: number widgets (traces, error rate, p95 latency, cost, tokens), traces and errors (stacked bars of `count` where `status <> 'error'` and where `status = 'error'`), tokens by type (spans of kind `llm` and `embedding`), error rate (bars, faded under 5 traces), scores (average per name, split), trace latency percentiles, LLM latency by model, time to first token, cost by model (stacked area of the top 3 models plus other), evaluation cost (traces of `cetra-eval`), top models by cost (a table of at most 10 models with each one's share of the cost; its rows open the trace list filtered to that model), top users by cost and top trace names by cost (horizontal bars of the 10 largest, D-C-21). The user page's Usage leaves out the evaluation cost and the top users.

**Moving charts** (members, D-C-18). Outside Edit, a member drags a widget by its title bar and resizes it from its corner on any dashboard they can edit, the Overview included. The new layout is shown at once and saved about 0.8 s after the last move, with the version the page read (on the Overview, the first save stores the project's copy). After a save, a bar under the header says "Layout saved" with "Undo" for 10 seconds; Undo saves the previous layout. A `409` drops the move, reloads the dashboard and says that someone else changed it; another failure drops the move and shows the error. Clicks on charts keep opening their buckets.

**Editing** (members). "Edit" turns the grid editable: widgets move and resize on a 60-column grid (`react-grid-layout`, D-C-19; the widget menu's Left, Right, Wider and Narrower move 5 columns), "Add widget" and "Add heading" append to the bottom, and each widget has Edit, Duplicate and Remove. The widget editor is a dialog with the source, the measures (aggregate, field, optional condition, label), the breakdown (field, limit, other), the widget filter (the filter bar of the source view), the chart type and its options, and a live preview over the dashboard's range. "Save" sends the whole definition with the version it loaded; a `409` says that someone else changed the dashboard and offers to reload. "Cancel" drops the changes; leaving the page with unsaved changes asks first. Below 768 px wide the grid becomes one column in `(y, x)` order and editing is off.

**Demo org** (D-C-17, D187). In an org with `demo: true`, for a user whose role there is viewer, the dashboard definitions are kept in localStorage (`cetra.dashboards.<org>/<project>`, one JSON list of `{id, name, description, definition, version, created_at, updated_at}`) instead of the dashboards API. Such a user sees the built-in Overview and their own localStorage dashboards, never the project's server dashboards, and may create, edit and delete them; the rules of 04 § Dashboards are checked in the browser, and the widget queries still run on the server. Another user cannot change these dashboards, so there is no version conflict. A banner in edit mode says that these dashboards are stored in this browser only. If the browser's storage is full or unavailable, saving fails with a message; dashboards changed in another tab appear when this tab's list refreshes.

**Interaction.** Charts use Recharts through shadcn `chart` (D128). Empty buckets are gaps for rates and percentiles. Hovering a chart moves a cursor on every time chart of the dashboard; only the hovered chart shows its tooltip. On a widget whose source is `traces` or `spans`, clicking a bucket opens that list filtered to the bucket, the widget's filter and the group (when the chart has one group and is not an area chart; otherwise the bucket opens without a group; the dashboard filter is added for `traces` widgets only, since it is a traces expression); dragging at least 8 px across two or more buckets zooms the range to them. Each chart is one keyboard stop: ←/→ move between buckets (announced, and marked with a line), Home/End jump to the ends, Enter opens the bucket's list (D-C-3). URL search params: `range` or `from` and `to`, `filter`, `group` (`model`, `environment` or `release`), `eval`, `exp`.

A settings sidebar replaces the project sidebar on settings routes: a Back link (to the current or last visited project, else the projects list), a scope switch between the project and the organization (D-L-6; the last visited project is remembered per org in the browser, so the project side stays one click away from organization pages), and the current scope's pages, starting with Overview; a filter box under Back searches both scopes by label, description and keywords and lists matches under Project and Organization; pages that exist at both levels (Members, Model prices, General) say which scope they edit and link to their counterpart; the footer shows the month's units against the plan (80 % and 100 % marks) and links to Plan. The project sidebar has a "Settings" entry at its bottom, and the org home has a "Settings" button.

`/:org/settings` and `/:org/:project/settings` are overview pages: one card per section the role can open, each with its icon, a one-line description and a live status taken from the endpoints the section's page already reads (for example "3 keys · last used 2h ago", "Retention 30 days", "2 connections, 1 failing", "Plan: Team · 62% of units used"). ⌘K lists every settings page the role can open, matched on the same keywords.

Every settings page has one layout: a header (title, one-line description, primary action at the right), content in bordered cards of the same maximum width, each form card with its own Save in its footer (enabled once the card has changes and is valid), and a red "Danger zone" card last. Fields validate as the user types. Leaving a page or closing a panel with unsaved changes asks "Discard unsaved changes?" first, and so does closing the tab. Number fields show their unit; slugs are read-only code chips with a copy button.

Lists (API keys, members, invites, personal tokens, LLM connections, channels, model prices, score definitions) are tables with a search box and sortable columns; search, sort and the open row are search params (`q`, `sort`, `desc`, `open`; the org members page also has `tab`). Lists are loaded page by page and searched and sorted over the loaded rows; the paged model price lists are searched by the server instead and keep the server order. Status pills show expired keys, failing connections and a channel whose last delivery failed. Selecting a row opens its panel in a drawer beside the list (`?open=<id>`), where it is edited, tested or deleted; create forms open the same panel (`?open=new`), except API keys, personal tokens and invites, whose dialogs show the secret or accept link once (D-L-5). Every destructive action (revoke, remove, delete, archive, leave) asks the user to type the item's name (or its key prefix, email or id when it has no name).

## Quality bar

- Trace list first paint < 1 s on 1B spans (server targets in D23); trace view usable with 10 000 spans (virtualized tree). Verified by bounded rendered-row counts in tests (D132): under 60 rows on a 5 000-trace list, under 80 rows in a fully expanded 10 000-span tree, at most 50 transcript detail requests before "Load more", and under 100 rows in a 20 000-key JSON tree.
- Keyboard: `/` focus search, `j/k` move in lists, `esc` close the split, `?` shortcuts help, and `g` then a letter to go to a project page: `d` Dashboard, `t` Traces, `p` Spans, `s` Sessions, `u` Users, `a` Alerts, `e` Evaluators, `o` Online rules, `r` Annotation queues, `m` Prompts, `l` Playground, `i` Datasets, `x` Experiments, `q` SQL (shown in the sidebar tooltips). Shortcuts are ignored while typing.
- Accessibility: shadcn/Radix primitives, focus management in the splits and in drawers, color not the only status signal.
- No external network calls from the UI (fonts and icons bundled), so air-gapped installs work.
