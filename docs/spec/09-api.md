All HTTP on one port (`CETRA_HTTP_ADDR`, default `0.0.0.0:8080`); OTLP/gRPC on `CETRA_GRPC_ADDR` (default `0.0.0.0:4317`); an OTLP/HTTP-only listener on `CETRA_OTLP_HTTP_ADDR` (default `0.0.0.0:4318`, serves only the OTLP routes `/v1/traces`, `/v1/logs`, `/v1/metrics` and `/v1/agent-context`) for exporters configured with the standard OTel port.

OpenAPI 3.1 generated by `utoipa`, served at `/api/openapi.json`; the TS SDK REST client and the UI API client are generated from it (`openapi-typescript`).

**The contract file (D69).** The generated document is also committed as `crates/server/openapi.json`. A test regenerates it and fails when the committed file differs, so every API change shows up in review. The UI and SDKs generate their clients from this file. Until an operation has a handler, it is declared with utoipa's builder API in `cetra_server::api::openapi`; when the handler lands, the declaration moves to `#[utoipa::path]` on the handler and the committed file must not change.

**Examples (D72).** `fixtures/api/` holds a small example project (stored spans and scores) and the responses the API returns for it, plus a `manifest.json` mapping operations to response files. The UI uses them as mocks; a test checks them against the Rust response types. See `fixtures/api/README.md`.

## Conventions

- JSON, `snake_case`. IDs: UUIDv7 strings; trace/span IDs as hex, lowercase in responses; requests may use either case.
- Instants are RFC 3339 UTC strings with 9 fractional digits (D64); durations (`*_ns`) are integers.
- Optional scalars are **omitted** when absent; lists and maps in response types are always present (possibly empty). Core types embedded in responses (`Score`, canonical messages) keep their own serde format. In the OpenAPI document an optional field is therefore not nullable. Two exceptions: the message and part fields that keep an explicit source `null` (D65, spec 01), and `next_cursor`, which is always present and `null` on the last page.
- `{project}` path segment accepts a project UUID or slug (`org-slug/project-slug` URL-encoded), or `current` when authenticated with an `sk` key (the key's project).
- Lists under `/api/v1`: `?limit=` (default 50, 1–1000; outside that range → 400; the internal usage export allows 1–10 000, default 1000) + `?cursor=` (opaque); response `{data: [...], next_cursor: string|null}` (`next_cursor` always present).
- Time range params: `from`, `to` (RFC 3339 with any offset, converted to UTC, or integer epoch milliseconds). The range is `[from, to)`; one bound alone leaves the other side open; `from >= to` is `400`.
- Credentials are accepted only in the `Authorization` header or the session cookie, never in a query string (D140).
- Errors: RFC 7807, content type `application/problem+json`: `{type: "about:blank", title, status, code, detail?, errors?: [{field, message, position?: {line, column}}]}`. `code` is a snake_case machine code (`bad_request`, `invalid_filter`, `query_failed`, `query_timeout`, `query_too_large`, `busy`, `restore_mode`, `unauthorized`, `forbidden`, `sso_required`, `email_not_verified`, `plan_limit`, `not_found`, `method_not_allowed`, `payload_too_large`, `unsupported_media_type`, `range_not_satisfiable`, `conflict`, `rate_limited`, `internal`, `too_many_traces`, `too_many_items`, `plan_required`, `quota_exceeded`, `owner_not_allowed`). `invalid_filter` (400) covers filter and SQL text; `query_failed` (400) covers execution errors; `query_timeout` and `query_too_large` are 422; `busy` is 503 (D94); `restore_mode` is 503 and says that this user-triggered outbound call is off because the server runs in restore mode (D-N-26); `method_not_allowed` is 405; `payload_too_large` is 413; `unsupported_media_type` is 415; `range_not_satisfiable` is 416 (D-G-23); `conflict` is 409; `sso_required`, `email_not_verified` `plan_required` (the org's plan does not include the feature, D-M-16) and `plan_limit` (the org's plan limit is reached; its detail names the limit, D178, D-K-14) are 403; `too_many_traces` (a filter deletion over 100,000 traces, D-M-5) is 422. `quota_exceeded` (the org's monthly units cap, D-P-17) is 402; `owner_not_allowed` (the internal org creation's owner is disabled or an instance admin, D-P-29) is 422. `position` (1-based, in characters) points into the field's value, for DSL and SQL errors. The device flow adds `authorization_pending`, `slow_down`, `access_denied` and `expired_token`, all 400 (08 § Device authorization). Messages go to the caller and are never logged.
- Idempotency: `Idempotency-Key` header honored on POSTs that create resources (24 h memory). Not implemented by any route yet (a cross-track gap; `POST /deletions` is not idempotent by key).
- Rate limit headers (`RateLimit-*`, IETF draft) on 429. Implicit visitors of the demo org get `429 rate_limited` with `Retry-After` above the limits of 08 § Demo org (D187).

### Playground

Track V M6 (D-V-20 to D-V-26, D-V-33 to D-V-37). One route, answered as a stream, and the rules around it.

| Method & path | Notes |
|---|---|
| `POST /playground/runs` | `RunPlayground` (D-V-26): members and above, through a session or a read-write PAT, never an API key. The body is `{connection_id, model, messages, variables?, placeholders?, params?, tools?, tool_choice?, response_format?, source?, render_variables?}` (D-V-21, D-V-38). The answer is `text/event-stream`: `start` `{trace_id}`, `text` `{delta}`, `tool_call` `{id, name, arguments}`, then `done` `{finish_reason, usage, cost_usd, latency_ms, ttft_ms, output}` or `error` `{class, message}`, with a `ping` every 15 s (D-V-20). A refusal before the stream is a problem answer: `400` with field errors, or `429 rate_limited` (D-V-24). |

- **Messages.** Each `messages` entry is a canonical message (01) or `{"type": "placeholder", "name": …}`, which is replaced in place by the messages given under that name in `placeholders`. `{{name}}` in the text parts written in `messages` is rendered from `variables`; placeholder messages are not rendered. `render_variables` (default `true`) turns that rendering off: when `false`, the request's own messages are sent as written, and placeholders are still expanded (D-V-38); the rendered-text budget still counts their text. A missing variable or placeholder is a `400` before the stream starts, with the field of the part (`messages[i].parts[j]`). At most 200 messages after placeholders, at most 4 MiB of rendered `text` parts (the request's own and the placeholders', `400` on `messages`), and a 2 MiB body (D-V-21, D-V-37). `source.prompt.name` follows the prompt name rule (1 to 200 characters, D-V-2) and `source.prompt.version` is at least 1; otherwise `400` on `source.name` or `source.version`.
- **Limits.** Per user, 60 runs a minute and 4 at once; per org, 16 at once. The user's and the org's limits are checked first, then the connection's slot and rate token: a run that waits at most 10 s for them and gets neither answers `429`, and that `429` still counts toward the user's 60 runs a minute (D-V-24, D-V-35). The wait takes the rate token first, then the slot; a token taken before a slot that never comes is spent. A call takes at most 300 s and fails after 60 s of silence, pings not counting (the provider's idle timeout is not restarted by them). `max_tokens` defaults to 4 096 and is at most 65 536.
- **Trace.** Each run is one trace with one `llm` span in the reserved environment `cetra-playground` (D-V-22, D-V-33). Playground spans are not units: they never count against the units cap or the usage counter (D-V-23). The default trace lists leave them out, and `include_eval` shows them. The run's trace is committed after the stream ends, also when the client cancelled. A cancelled run has status error and the message `cancelled`, and its provider call is dropped.
- **Connection status.** A run uses the connection whatever its `status`, and never marks it failing (D-V-36).
- **Tools.** Tools are never run. A tool-mode response format forces its own tool, so the user's tools are not callable in the same run. Media and unknown parts are refused (D-V-25).
- **Notes.** Playground traces carry no end-user id, so a delete-by-user never matches them; they go with project and trace deletions. The overview's "Evaluation cost" widget counts `cetra-eval` only.
- **Audit and restore.** The audit log records `playground run` with ids, the outcome and the latency, never the payload. Restore mode refuses runs (D-N-25).

Adds the targets of the newest occurrences of the issue and of the seven merged issues with the most occurrences in the last 14 days, in any issue state: a trace queue gets each occurrence's trace, a span queue its span (the `cetra.issue.span_id` of the occurrence; error issues and span-level candidates have it), a session queue its session, each target once, at most `limit` targets. An occurrence without that target is skipped ("the occurrence has no trace", "…no span", "…no session"; `index` is its position among the occurrences read newest first). Everything else is AQ's add: the data window, evaluation traces, the deletion guard re-checked in the insert transaction, one item per target, past 100 000 items `422` `too_many_items` with nothing added (D-AQ-8). Permission `ManageQueues`: members and above with a session, a read-write personal access token or an API key with `write`. `400` on `limit` and on `issue` when the issue has no occurrence in the data window; `404` for a missing issue or queue (a queue of another project too); the answer is `201` whatever the counts, also when every occurrence is skipped (D-IC-30) |

Errors use the usual problem document (§ Conventions). Issue JSON uses RFC 3339 instants.

- **Stream.** Each event's data is a JSON object:
  - `start` `{turn_id, trace_id}`: `turn_id` is the sequence number of the stored user message; `trace_id` is 32 hex characters.
  - `text` `{delta}`; `tool_call` `{id, name, arguments}`.
  - `tool_result` `{id, ok, summary}`: `summary` holds `size_bytes`, `rows` when the answer has rows and `error_code` when it failed; the full answer is in the stored message.
  - `draft` `{id, kind, draft}`: `id` is `draft_<tool call id>`; `kind` is `filter`, `sql`, `dashboard`, `evaluator` or `online_rule`.
  - `done` `{finish_reason, usage: {input, output}, cost_usd, steps}`: `finish_reason` is the model's (`stop` when it sends none) or `limit`; `cost_usd` sums the model calls' cost and is `null` without a price; `steps` counts the model calls.
  - `error` `{class, message}`: `class` is `retryable`, `pause` or `permanent`; the message holds no payload text.
  - A `ping` every 15 s. Aborting the request cancels the turn: the provider call is dropped and the partial answer is stored as `cancelled`. A turn is not a live stream (D-AS-9).
- **Turn limits.** Per user, 20 turns a minute and 2 at once; per org, 8 at once; per conversation, one at a time (`409`) (D-AS-15). Per turn: 16 model calls, 32 tool calls and 10 minutes; `max_tokens` 4,096 per call. A model call waits at most 10 s for its connection's slot and rate token, else the turn ends with `error` `retryable` "the LLM connection is busy" (D-AS-8). Reaching a limit stores an assistant message that names it and ends with `done` `finish_reason: "limit"`; tool calls beyond the 32nd are not run (D-AS-23). The history sent to the model is at most 100,000 estimated tokens (D-AS-15, D-AS-22).
- **Stored messages.** The user message is stored first. Each model call stores an assistant message (its text, then its tool calls); a tool message follows its results, each followed by the draft it produced (D-AS-21). Every message of the turn carries the turn's trace id. Tool results are stored in full and stubbed by an hourly sweep after 24 hours, so a result can stay whole for up to about 25 hours: the part keeps `size_bytes`, `rows` and `stubbed: true`, and the API omits `result` (D-AS-12).
- **Trace.** Each turn is one trace in the reserved environment `cetra-assistant`, metadata only: an `agent` root, an `llm` span per model call and a `tool` span per tool call, with no message text, arguments or results. Its spans are not units (D-AS-11, D-V-23).
- **Audit and restore.** The audit log records `assistant turn started` and `assistant turn` with the ids, the step and tool counts and the outcome, never the payload. Restore mode refuses turns and the setting test (D-AS-16).

## Response shapes (observability read API)

Field lists live in the Rust types (`cetra_server::api`) and the contract file; these are the rules behind them (D70, D73).

- **Payloads are parsed.** Span `input` / `output` are returned as `{format: "messages", value: Message[]}`, `{format: "json", value: <any JSON>}` or `{format: "text", value: string}`. Stored text that does not parse as its declared format degrades instead of failing: `messages` that are not a message array → `json` if the text is JSON, else `text`; `json` that does not parse → `text`. `request_params`, `system_instructions`, `tool_definitions` and event/link `attributes` are returned as parsed JSON (the raw string when it does not parse). `attributes`, `resource_attributes` and `metadata` stay string maps, as stored.
- **Light vs full span.** `SpanSummary` carries the light (**P**) columns of spec 01 except `project_id`, `request_model`, `response_model`, `cost_input`, `cost_output`, plus the computed `duration_ns` and `model`. `SpanDetail` carries every column except `project_id`.
- **Trace detail** = `{trace: TraceSummary, spans: [{depth, detached, span: SpanSummary}], truncated}`. `spans` is a flat list in **pre-order**: roots first, children sorted by `(start_time, span_id)`. A span whose parent is missing (or that sits in a parent cycle) is emitted as a root with `detached: true`. Duplicate span IDs keep the first row. At most 20 000 spans (earliest by `start_time`); `truncated: true` when more exist. The tree is assembled in Rust without recursion.
- **Scores on rows.** `TraceSummary.scores` and `SessionSummary.scores` hold the latest score (greatest `updated_at`, then greatest `score_id`) of each name attached to that trace or session, sorted by name. Full score lists come from `GET /scores`.
- **Session detail** = `{session: SessionSummary, turns: [{trace: TraceSummary, input?, output?}], truncated}`: traces by `start_time`, at most 1 000; `input`/`output` are the root span's payloads (absent when the trace has no root).
- **User detail** = `{user: EndUserSummary, sessions: SessionSummary[]}`: the user's 100 most recent sessions. `EndUserSummary.error_count`, like `SessionSummary.error_count`, is the sum of the traces' `error_count`.
- **Default exclusions** (05) apply to the trace, span, session and user lists, to session/user detail and to dashboard queries; not to trace/span detail or scores. Every endpoint they apply to accepts `include_eval` and `include_experiments`.
- **Saved views** store `state` as an opaque JSON object owned by the UI (its URL search params); the server only checks that it is an object.

## SSE

`text/event-stream`, `event:` names `span`, `trace`, `resync`, `ping` (every 15 s). Data = JSON of the light columns: `span` events carry a `SpanSummary`, `trace` events a `TraceSummary`, `resync` and `ping` an empty object. `span` and `trace` events carry an `id:` that increases over the process's life. Nothing is replayed: a request with `Last-Event-ID`, or a subscriber that fell behind the live bus, first gets `resync`, and the client refetches (D-G-12). Auth by cookie (UI) or bearer. Max 100 concurrent streams per user (per key for an API key); one more is `429` `rate_limited`. Responses send `Cache-Control: no-cache` and `X-Accel-Buffering: no`. Every stream ends when the server shuts down, 15 minutes after it opened, and when its client has not read for 30 s; the span stream also ends after 10 minutes without a span (D-G-34). The client reconnects, which authenticates again, and refetches. A score write sends no event: an open list or trace shows a new score after the trace's next span or a refetch. The trace stream's `search` is checked over the arriving spans' time range: only spans that arrive while the stream is open can match (D-G-33).

## MCP server

Streamable HTTP at `POST /mcp`, stateless, JSON responses, implemented with the `rmcp` crate (D-H-2). There is no stdio bridge in the MVP. Auth: `Authorization: Bearer pat-…` only; a read-only PAT is enough; a cookie or an `sk` key is `403` (D-H-3). Per PAT: 60 requests a minute and 4 at a time, then `429 rate_limited` (D-H-10).
