title: LLM connections
description: Connect cetra to a model provider so LLM judges can call a model.

An LLM connection stores a provider and an API key, so evaluators can call a model on your behalf.

## Supported providers

A connection uses one of three provider APIs:

| Provider | Notes |
|---|---|
| OpenAI | Also any server with an OpenAI-compatible chat endpoint (Azure OpenAI, vLLM, Ollama, a gateway): set the base URL. |
| Anthropic | Messages API. |
| Gemini | Google's `generateContent` API. |

## Add a connection

Connections belong to the organization, so every project of the org can use them. Every member can see them, and org admins add, edit, delete and test them.

1. Open the organization's **LLM connections** page and select **Add connection**.
2. Choose the provider, give the connection a name and paste the API key.
3. Optional: set a base URL, a default model and extra headers.
4. Save, then select **Test**. The test makes one small judge call and shows whether it worked and how long it took.

The same works over the API:

```bash
curl -X POST http://localhost:8080/api/v1/orgs/<ORG>/llm-connections \
  -H "Authorization: Bearer <PAT>" \
  -H "Content-Type: application/json" \
  -d '{ "name": "openai", "adapter": "openai", "api_key": "<PROVIDER_API_KEY>", "default_model": "gpt-5-mini" }'
```

Two settings limit the load a connection puts on the provider, shared by every rule that uses it: the number of calls running at once (default 4) and the calls per minute (default 300).

### Structured output

A judge must answer in a fixed shape. The connection's structured output mode says how to ask for it:

| Mode | What cetra does |
|---|---|
| `native` (default) | Uses the provider's JSON-schema response format. |
| `tool` | Forces a tool or function call that carries the schema. |
| `prompt` | Adds the schema to the prompt and parses the text. |

If a provider rejects the mode, the judge fails with an error that names the setting to change. cetra does not switch modes by itself.

## The assistant

The in-app assistant uses one of your organization's connections. An org admin picks it in Organization settings → Assistant. Deleting that connection turns the assistant off. A connection marked failing still serves the assistant. See [Assistant](/docs/platform/assistant/).

## How keys are stored

cetra encrypts the API key and any extra header values with the instance's encryption key before it writes them to the database. The UI and the API never show them again: they show only the last 4 characters of the key and the header names. To replace a key, edit the connection and enter a new one.

If you run cetra yourself, see [Configuration](/docs/self-hosting/configuration/#secrets) for how to set and rotate the instance key.

## Private networks

cetra blocks outbound requests to private addresses (loopback, private ranges, link-local and similar), so a connection cannot reach services inside your network. To use a local model server such as Ollama or vLLM, an operator sets `security.allow_private_network_egress` to `true` in the server configuration. The UI cannot read that setting, so the connection form only explains it. The same setting covers webhook evaluators and other outbound calls.

## When a connection fails

If the provider answers with an authentication, billing, quota or not-found error, cetra marks the connection as failing and pauses every online rule that uses it. A successful test or a new key resumes them.
